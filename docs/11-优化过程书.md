### 09-24 · 从「能跑」到「别人也能跑」

**做了双击即可运行的 `.bat`。** 起因是用户反馈「命令行步骤太绕」。
代价是踩了两个 Windows 的坑：`dirname: command not found`（Git Bash 的路径
和原生 Windows 程序不互通）、GBK 输出让 awk 静默不匹配。

**修 `new-keystore.sh` 传给 keytool 的是 MSYS 路径** —— 在 Git Bash 里
`/c/Users/...` 这种路径原生 Java 认不出来。

**真机首次运行，抓到一个启动崩溃的真 bug。** 这类问题只有真机才暴露 ——
模拟器上一切正常。

**五条产品反馈落地，其中一条撤掉了 Coil 3。** 加 Coil 3 之后 Gradle 依赖图
序列化异常，编译链直接红。**结论：这个项目的依赖矩阵很脆，能不加依赖就不加。**

**生成菜谱配图，踩到「并行调用互相覆盖文件」。** 并行 11 个请求只活下来 8 个，
3 张的积分白花。**结论：生成图片一律串行。**

**用户否掉了程序绘制的插画。** 原话「你画的是啥东西？？」
**改成真实食材照片 + 纯白底 + 单个主体 + 产品摄影质感**，
补齐 40 张真实白底食材图。

**文档缺陷两连击：** ① 文档里给网址加了粗，用户复制时把 `**` 也复制进去了；
② 文档里猜的字段名是错的（`mode` 根本不存在）。**结论：文档里的字段名必须
从代码里核出来，不能凭印象写。**

### 09-25 · 推上 GitHub，跑通 CI

**修菜谱页同一道菜重复出现。** 用户多点几次「生成新菜谱」，
MOCK 模式反复给同样几道菜，库里就攒出十几条同名行。
**修法：生成式内容落库必须按业务键 upsert，不能无条件 INSERT。**

**口味偏好改成折叠收集箱** —— 一屏塞十几个输入框太挤。

**踩坑：debug 包的后端地址默认是模拟器地址。** 真机上 App 会**静默**退回登录页，
看起来像账号被清空。**修法：`build-debug.bat` 自动检测局域网 IP 并注入。**

**踩坑：`.bat` 里 `chcp 65001` 和非 ASCII 不能同时出现。** chcp 之后 cmd
按**字符偏移**而不是字节偏移继续读文件，文件里有中文就会静默跳过后续行。

**签名密钥生成、代码推上 GitHub、CI 首次跑通。** CI 调试踩了三个坑：
workflow 文件首次推送不触发构建；`setup-android` 必须 `@v4`；
国内镜像和 GBK 编码在海外 Linux runner 上都有害。

### 09-29 · 接上真实 AI（项目最重要的一个坎）

**上午：修折叠箱里勾选开关的卡顿与闪烁。**

> 三个坑：① `busy` 是全局的，勾一个开关会让同卡所有开关一起灰掉；
> ② 等服务器回包界面才动，手感「一卡一卡」；③ 保存后再 `load()` 会多跑请求
> 且开关先回弹。
> **修法：乐观更新 + 防抖 350ms，失败才 `load` 回滚。**
> ⚠️ **这个坑在 privacy 修过一次、health 又漏了** —— 加新开关时照抄 `updateHealth`。

**🎉 接上真实 AI（百炼 API Key 配好）。** 项目从此不再是 MOCK 模式。

实测：

| 操作 | 耗时 | 结果 |
|---|---|---|
| 拍照识别 · 1 样 | 3.4 秒 | 西兰花 0.98 |
| 拍照识别 · 40 样 | 51.5 秒 | 40 种一个不漏 |
| 菜谱生成 · 3 道 | 20.0 秒 | 结构完整 |

> **关键印证**：AI 会**自己推出** `category`、`storage_location`、
> `shelf_life_days`。所以「食材库要扩到大众冰箱规模」的真实工作量是
> **补图片**，不是补名称表。

**修检测脚本的假警报。** `check_ai.py` 用 1×1 的透明 PNG 测视觉模型，
模型直接拒收 —— 这一项**永远不可能通过**，还会给出完全错误的排查建议。

**上传前压缩图片。** 客户端把原图直接上传，手机 5000 万像素照片可能超过
10MB 上限，而报错信息让用户「压缩后再上传」——**App 自己没这功能**。

| | 压缩前 | 压缩后 |
|---|---|---|
| 尺寸 | 4096×3072 | **1200×1600** |
| 体积 | 2.0MB | **163KB** |

> ⚠️ 重编码会丢 EXIF 旋转 → **竖拍照片会变横的，AI 看到一台躺倒的冰箱**。
> 必须手动读 `android.media.ExifInterface` 转正。
>
> ⚠️ **四条图片路径必须都覆盖**：头像 / 广场发帖 / 相册选图 / 相机拍照。
> 相机走 CameraX 直接写文件，**绕过相册那条路** —— 差点只改一半。

**修「菜谱生成来来回回就那几道」。**

实测连点三次，前两道菜一模一样：

```
第 1 次: 番茄炒蛋、青椒鸡胸肉、西兰花豆腐炒饭
第 2 次: 番茄炒蛋、青椒鸡胸肉、西兰花豆腐炒鸡丁   ← 前两道重复
第 3 次: 番茄炒蛋、青椒鸡胸肉、西兰花豆腐炒蛋
```

**根因**：提示词里完全没提用户已经有什么菜。而落库是按菜名 upsert 的，
重复的名字只覆盖旧行、不新增 —— 所以点多少次列表都长不大。

**修法**：生成时把已有菜名传给模型，明确写「请勿重复」。
修复后同样连点三次 → **9 道零重复**。

**修食材配错图。** 图片规则对加工食品太宽：

| 食材 | 配成了 | 原因 |
|---|---|---|
| 牛油果 | 牛排 | 被 `beef` 的单字「牛」抢走 |
| 花生米 | 米饭 | 被 `rice` 的单字「米」抢走 |
| 鱿鱼 | 鱼 | 被 `fish` 的「鱼」抢走（海鲜规则白写） |
| 番茄酱 | 新鲜番茄 | 含「番茄」 |
| 花生油 | 一堆花生米 | 含「花生」 |

**配错图比没图更糟** —— 用户会以为识别错了，而不是以为缺图。
修法：加「挡刀区」，把这类规则拦在原料规则前面。

### 10-04 · 冰箱页分类体系

**需求**：① 食材自动分类 + 用户自定义折叠箱；② 图库里没有的食材要能
自动归到对应分类并配「万能图」。

**分类体系**：9 个默认分类（蔬菜/水果/肉类/水产/蛋奶/豆制品/主食/调味/其他）。
分类有三个来源，优先级从高到低：**图片 key > 名字推断 > AI 返回值**。

> 图片 key 排第一是为了保证「分类」和「配图」一致 ——
> 不让食材出现在水果组里却配一张蔬菜图。
>
> 名字推断排在 AI 前面，是因为它**不依赖 AI**：手动添加的食材、
> MOCK 模式下的食材都能分组，而且同一个名字永远同一类，结果稳定。

**万能图兜底**：`具体图 → 分类万能图 → 占位`。
图库里没有的「杨桃」会自动退到「水果」的万能图。

**顺带修掉一批配错图/分错类** —— 见上面 09-29 那张表。

**自定义折叠箱（后端）**：两张新表 + 6 个接口。用户确认了两个决定：
**能同时进多个箱子**（多对多）、**和默认分类并存**。

> 守住两条红线：**删箱子不删食材**（只解除归组）、**不依赖 `ON DELETE CASCADE`**
>（SQLite 默认不开外键约束，CASCADE 不生效，会留下孤儿关联行且不报错）。

> ⚠️ **踩到一个极难查的坑**：204 接口启动时报
> `Status code 204 must not have a response body`，但一模一样的写法在别的文件里没事。
> 根因是文件顶部的 `from __future__ import annotations` 把 `-> None`
> 变成字符串，FastAPI 解析出 `NoneType` 类型对象，而 `bool(NoneType)` 是 True。
> **报错位置和真正原因完全不在一处。**

### 10-04 下午 · 生产数据库接通（Supabase）

**Supabase 项目建好并验证通过。**

| 项 | 结果 |
|---|---|
| 数据库连接 | ✅ 连接池 2.3 秒通，**20 张表自动建好** |
| 图片 bucket | ✅ `fridge-photos`（公开）已创建并双向验证 |
| `.env` | ✅ 三个值全部配好 |

**过程中挖出三个坑：**

**① Supabase 新版令牌默认「No access」。** 第一次给的令牌只有身份验证、
读不了任何东西（403）。必须手动勾 `Project → Read` 和 `Application services → Read`。

**② 本机网络按 SNI 拦截 `*.supabase.co`。** 诊断过程：

```
同一个 Cloudflare IP，只换 SNI：
  SNI = <项目>.supabase.co   ✗ 连接被重置
  SNI = api.supabase.com      ✓ TLSv1.3
  SNI = www.cloudflare.com    ✓ TLSv1.3
  www.google.com              ✗ 超时（说明是 GFW 级别，不是本机代理）
```

域名前置（换 SNI + 改 Host 头）被 Cloudflare 挡了（403）。

**影响很小**：数据库走 PostgreSQL 协议不受影响；只有 Storage 上传在本地失败，
按设计退回本地磁盘。服务器上没这个问题。

**③ 创建 bucket 的两条绕行路。** 管理 API 只有读 bucket 的接口、没有创建的。
于是：**直接往 `storage.buckets` 表插一行**（bucket 元数据就存这儿，
和 Storage API 内部做的事一样），再用管理 API 独立确认。
已写进 `docs/03`。

**另外一个提醒**：配好之后本地 `.env` 就指向生产库了，
**不能跑 `tests/test_e2e.py`** —— 它会注册几十个测试账号进去。

### 10-06 · 食材图库扩到 582 张，匹配能力大改

**Ethan 在外部程序生成了 574 张食材图**（12 个顶层分类、35 个子类，
带一份完整的清单 CSV）。这批图让食材配图从「40 张、大面积缺图」
变成「基本全覆盖」。

| | 之前 | 现在 |
|---|---|---|
| 食材图 | 40 张 | **582 张**（17MB） |
| 冰箱实测覆盖 | 24/37 | **34/37** |
| 匹配方式 | 手写关键词规则 | **词库 + 五级降级** |
| 分类 | 9 个 | **12 个**（和清单对齐） |

#### ① 图片导入

574 张 1024×1024 压到 512×512：**94.1MB → 14.7MB**（省 84%）。
给 `tools/import-images.py` 加了 `--src` 参数，可以直接指向外部目录，
不用先把图搬进 `.tmp-images-ingredients/`。

导入前**备份了原有的 40 张**（里面有 4 张是 Ethan 早先提供的真实照片）。

#### ② 从清单自动生成词库

574 条「中文名 → 图片 key → 分类」如果手写，等于把同一份数据抄第二遍，
改一处就会两边不一致。改成**生成**：

```
backend/data/ingredient-manifest.csv   ← 唯一数据源
        ↓ tools/build-ingredient-lexicon.py
backend/app/services/ingredient_lexicon.py   ← 自动生成，不要手改
```

#### ③ ⭐ 匹配改成五级降级（Ethan 提的核心需求）

他提的场景：**用户输「肥羊肉」，库里没有这个词，但要能理解是羊肉。**

| 级 | 依据 | 例子 |
|---|---|---|
| ① 挡刀区 | 手写规则，防加工品误配 | 番茄酱 → seasoning |
| ② 词库精确 | 574 条标准名 | 五花肉 → pork-belly |
| ③ 别名 | 手写高频俗称 | 车厘子 → cherry |
| ④ **词库子串** | 名字被包含，**最长优先** | **肥羊肉 → 羊肉** |
| ⑤ 关键词兜底 | 手写规则 | — |

实测：

```
肥羊肉 → lamb        内蒙古羔羊肉 → lamb     新鲜菠菜 → spinach
小番茄 → tomato      冷冻虾仁 → peeled-shrimp  澳洲牛排 → beef-steak
```

**最长优先**是关键：按名字长度倒序扫，第一次命中就是最长的那个。
所以「新鲜杏鲍菇」会命中「杏鲍菇」而不是「杏」。

> ⚠️ 子串匹配里**跳过了 1 字条目** —— 单字太容易误伤：
> 「梨」会命中「凤梨酥」、「杏」会命中「银杏」。单字只在精确匹配时生效。

#### ④ 顺带把分类扩到 12 个

原来 9 个分类塞不下清单的体系（清单有 63 条饮品、49 条零食），
硬塞会让「其他」变成杂物堆。改成和清单对齐的 12 个：
蔬菜/水果/肉类/水产/蛋奶/豆制品/主食/坚果/调味/饮品/零食/其他。

#### ⑤ 发现并修掉的误判

| 现象 | 根因 | 修法 |
|---|---|---|
| 覆盆子 → 其他 | **「覆盆子」三个字里没有「莓」**，靠单字「莓」兜不住 | 明确写进水果关键词 |
| 杏仁 → 水果 | 「杏仁」含「杏」 | 坚果例外区排在水果之前 |
| 南瓜子 → 蔬菜 | 含「瓜」 | 同上 |
| 葡萄柚 → 无图 | 清单里只有「柚子」 | 指向 pomelo（外观接近） |

#### ⑥ 让位给词库

挡刀区里有些规则是**当时因为没图才加的**（生抽、老抽、蚝油、料酒…），
现在词库有更精确的 key（`light-soy-sauce` / `oyster-sauce` / `cooking-wine`），
拦成笼统的 `seasoning` 反而是倒退 —— 全部让位。

**测试同步更新**：规则 77 项、分类 99 项、端到端 276 项，全过。

### 10-06 下午 · 菜品库：192 道家常菜 + 食材关联

**需求**：基于已有的 582 种食材，建一个菜品库，让冰箱里的食材能推出相关菜品；
同时给 Ethan 一份「菜名 + 生图描述」的表，他去外部生图。

#### ① 菜品清单（192 道）

| 分类 | 数量 | 举例 |
|---|---|---|
| 家常热菜 | 106 | 西红柿炒鸡蛋、红烧肉、宫保鸡丁、麻婆豆腐 |
| 主食 | 23 | 蛋炒饭、番茄鸡蛋面、饺子、葱油饼 |
| 汤羹 | 21 | 紫菜蛋花汤、冬瓜排骨汤、银耳莲子汤 |
| 小吃点心 | 20 | 春卷、锅贴、蛋挞、糖葫芦 |
| 凉菜 | 12 | 凉拌黄瓜、皮蛋豆腐、口水鸡 |
| 早餐 | 10 | 小米粥、皮蛋瘦肉粥、茶叶蛋 |

**每一道都标注了必需食材和可选食材**，用的是词库里的标准名，
并且生成时**校验每个食材名都能解析出 key** —— 解析不了直接报错退出，
因为关联不上的菜在推荐时永远匹配不到。

#### ② 又扫出 19 个词库缺口

写清单时发现一些**家庭常做菜的常客词库里没有**：

```
西兰花 / 花椰菜 / 菜花    ← 清单里叫「羽衣甘蓝」，但日常都说西兰花
卷心菜 / 紫甘蓝 / 甘蓝    ← 清单里叫「大白菜/小白菜」
香椿                     ← 词库有「香椿芽」，但反向包含匹配不到
豆苗 / 可乐 / 雪碧 / 酸笋 / 椰蓉 / 梅花肉 / 前腿肉 / 鸭掌 / 鸭肠 …
```

全部补进 `EXTRA_ALIASES`。

**「香椿」这个坑值得记**：词库里是「香椿芽」（更长的名字），
而子串匹配是「词库名被查询名包含」—— `"香椿芽" in "香椿"` 是 False ✗
**反向包含捞不到**，只能显式加别名。

#### ③ 让位给词库（第二例）

「淀粉」的挡刀规则把**木薯淀粉、红薯淀粉**这些具体的也拦了，
导致它们拿不到自己的专属图。改成只在别名表里处理笼统的「淀粉」，
具体的交给词库。

> 这是同一个模式第二次出现：**早期为「没图」加的临时规则，图补齐后要回头清理。**
> 上次是生抽/蚝油，这次是淀粉。

#### ④ 必需食材 vs 可选食材

反向索引一开始把两者混在一起，结果**「蒜」关联了 36 道菜** ——
用户冰箱里有蒜，就以为能做 36 道，点进去发现什么都缺。

改成两张索引：

- `BY_REQUIRED`（推荐用）—— 只有必需食材才算「能做」
- `BY_ANY`（搜索用）—— 含可选食材，搜「鸡蛋」能找到所有用到鸡蛋的菜

```
        ↓ tools/build-dish-library.py
backend/app/services/dish_library.py   ← 代码用的菜品库
docs/12-菜品生图表.md                  ← 给 Ethan 的生图表
```

## 更新约定

**每次做完一次优化，往「时间线」里追加一条**，格式如下：

```markdown
### MM-DD HH:MM · 一句话说清改了什么

**问题**：为什么要改？不改会怎样？（用户反馈 / 自己发现 / 踩坑）
**改动**：具体改了什么。涉及取舍的把取舍写出来。
**结果**：**必须带可验证的数字或现象**，不要只写「已优化」。
**提交**：<commit hash>
```

### 写的时候注意

1. **结果必须可验证。** 「已优化」不算结果，「2MB → 163KB」才算。
2. **踩的坑要单独标出来。** 这类内容对后来的人价值最高。
3. **取舍要写。** 「为什么不用方案 B」比「用了方案 A」更有信息量。
4. **当天就写。** 隔天再回忆会漏掉细节 —— 这份文档的价值全在细节上。
5. **总览表要同步更新**（测试数、表数、配图数这些数字）。

> 如果一次优化跨了好几天（比如等外部账号），
> 就在完成那天记一条，把等待的原因写进「问题」里。
