### 09-24 · 从「能跑」到「别人也能跑」

**做了双击即可运行的 `.bat`。** 起因是用户反馈「命令行步骤太绕」。
代价是踩了两个 Windows 的坑：`dirname: command not found`（Git Bash 的路径
和原生 Windows 程序不互通）、GBK 输出让 awk 静默不匹配。

**修 `new-keystore.sh` 传给 keytool 的是 MSYS 路径** —— 在 Git Bash 里
`/c/Users/...` 这种路径原生 Java 认不出来。

**真机首次运行，抓到一个启动崩溃的真 bug。** 这类问题只有真机才暴露 ——
模拟器上一切正常。

**五条产品反馈落地，其中一条撤掉了 Coil 3。** 加 Coil 3 之后 Gradle 依赖图
序列化异常，编译链直接红。**结论：这个项目的依赖矩阵很脆，能不加依赖就不加。**

**生成菜谱配图，踩到「并行调用互相覆盖文件」。** 并行 11 个请求只活下来 8 个，
3 张的积分白花。**结论：生成图片一律串行。**

**用户否掉了程序绘制的插画。** 原话「你画的是啥东西？？」
**改成真实食材照片 + 纯白底 + 单个主体 + 产品摄影质感**，
补齐 40 张真实白底食材图。

**文档缺陷两连击：** ① 文档里给网址加了粗，用户复制时把 `**` 也复制进去了；
② 文档里猜的字段名是错的（`mode` 根本不存在）。**结论：文档里的字段名必须
从代码里核出来，不能凭印象写。**

### 09-25 · 推上 GitHub，跑通 CI

**修菜谱页同一道菜重复出现。** 用户多点几次「生成新菜谱」，
MOCK 模式反复给同样几道菜，库里就攒出十几条同名行。
**修法：生成式内容落库必须按业务键 upsert，不能无条件 INSERT。**

**口味偏好改成折叠收集箱** —— 一屏塞十几个输入框太挤。

**踩坑：debug 包的后端地址默认是模拟器地址。** 真机上 App 会**静默**退回登录页，
看起来像账号被清空。**修法：`build-debug.bat` 自动检测局域网 IP 并注入。**

**踩坑：`.bat` 里 `chcp 65001` 和非 ASCII 不能同时出现。** chcp 之后 cmd
按**字符偏移**而不是字节偏移继续读文件，文件里有中文就会静默跳过后续行。

**签名密钥生成、代码推上 GitHub、CI 首次跑通。** CI 调试踩了三个坑：
workflow 文件首次推送不触发构建；`setup-android` 必须 `@v4`；
国内镜像和 GBK 编码在海外 Linux runner 上都有害。

### 09-29 · 接上真实 AI（项目最重要的一个坎）

**上午：修折叠箱里勾选开关的卡顿与闪烁。**

> 三个坑：① `busy` 是全局的，勾一个开关会让同卡所有开关一起灰掉；
> ② 等服务器回包界面才动，手感「一卡一卡」；③ 保存后再 `load()` 会多跑请求
> 且开关先回弹。
> **修法：乐观更新 + 防抖 350ms，失败才 `load` 回滚。**
> ⚠️ **这个坑在 privacy 修过一次、health 又漏了** —— 加新开关时照抄 `updateHealth`。

**🎉 接上真实 AI（百炼 API Key 配好）。** 项目从此不再是 MOCK 模式。

实测：

| 操作 | 耗时 | 结果 |
|---|---|---|
| 拍照识别 · 1 样 | 3.4 秒 | 西兰花 0.98 |
| 拍照识别 · 40 样 | 51.5 秒 | 40 种一个不漏 |
| 菜谱生成 · 3 道 | 20.0 秒 | 结构完整 |

> **关键印证**：AI 会**自己推出** `category`、`storage_location`、
> `shelf_life_days`。所以「食材库要扩到大众冰箱规模」的真实工作量是
> **补图片**，不是补名称表。

**修检测脚本的假警报。** `check_ai.py` 用 1×1 的透明 PNG 测视觉模型，
模型直接拒收 —— 这一项**永远不可能通过**，还会给出完全错误的排查建议。

**上传前压缩图片。** 客户端把原图直接上传，手机 5000 万像素照片可能超过
10MB 上限，而报错信息让用户「压缩后再上传」——**App 自己没这功能**。

| | 压缩前 | 压缩后 |
|---|---|---|
| 尺寸 | 4096×3072 | **1200×1600** |
| 体积 | 2.0MB | **163KB** |

> ⚠️ 重编码会丢 EXIF 旋转 → **竖拍照片会变横的，AI 看到一台躺倒的冰箱**。
> 必须手动读 `android.media.ExifInterface` 转正。
>
> ⚠️ **四条图片路径必须都覆盖**：头像 / 广场发帖 / 相册选图 / 相机拍照。
> 相机走 CameraX 直接写文件，**绕过相册那条路** —— 差点只改一半。

**修「菜谱生成来来回回就那几道」。**

实测连点三次，前两道菜一模一样：

```
第 1 次: 番茄炒蛋、青椒鸡胸肉、西兰花豆腐炒饭
第 2 次: 番茄炒蛋、青椒鸡胸肉、西兰花豆腐炒鸡丁   ← 前两道重复
第 3 次: 番茄炒蛋、青椒鸡胸肉、西兰花豆腐炒蛋
```

**根因**：提示词里完全没提用户已经有什么菜。而落库是按菜名 upsert 的，
重复的名字只覆盖旧行、不新增 —— 所以点多少次列表都长不大。

**修法**：生成时把已有菜名传给模型，明确写「请勿重复」。
修复后同样连点三次 → **9 道零重复**。

**修食材配错图。** 图片规则对加工食品太宽：

| 食材 | 配成了 | 原因 |
|---|---|---|
| 牛油果 | 牛排 | 被 `beef` 的单字「牛」抢走 |
| 花生米 | 米饭 | 被 `rice` 的单字「米」抢走 |
| 鱿鱼 | 鱼 | 被 `fish` 的「鱼」抢走（海鲜规则白写） |
| 番茄酱 | 新鲜番茄 | 含「番茄」 |
| 花生油 | 一堆花生米 | 含「花生」 |

**配错图比没图更糟** —— 用户会以为识别错了，而不是以为缺图。
修法：加「挡刀区」，把这类规则拦在原料规则前面。

### 10-04 · 冰箱页分类体系

**需求**：① 食材自动分类 + 用户自定义折叠箱；② 图库里没有的食材要能
自动归到对应分类并配「万能图」。

**分类体系**：9 个默认分类（蔬菜/水果/肉类/水产/蛋奶/豆制品/主食/调味/其他）。
分类有三个来源，优先级从高到低：**图片 key > 名字推断 > AI 返回值**。

> 图片 key 排第一是为了保证「分类」和「配图」一致 ——
> 不让食材出现在水果组里却配一张蔬菜图。
>
> 名字推断排在 AI 前面，是因为它**不依赖 AI**：手动添加的食材、
> MOCK 模式下的食材都能分组，而且同一个名字永远同一类，结果稳定。

**万能图兜底**：`具体图 → 分类万能图 → 占位`。
图库里没有的「杨桃」会自动退到「水果」的万能图。

**顺带修掉一批配错图/分错类** —— 见上面 09-29 那张表。

**自定义折叠箱（后端）**：两张新表 + 6 个接口。用户确认了两个决定：
**能同时进多个箱子**（多对多）、**和默认分类并存**。

> 守住两条红线：**删箱子不删食材**（只解除归组）、**不依赖 `ON DELETE CASCADE`**
>（SQLite 默认不开外键约束，CASCADE 不生效，会留下孤儿关联行且不报错）。

> ⚠️ **踩到一个极难查的坑**：204 接口启动时报
> `Status code 204 must not have a response body`，但一模一样的写法在别的文件里没事。
> 根因是文件顶部的 `from __future__ import annotations` 把 `-> None`
> 变成字符串，FastAPI 解析出 `NoneType` 类型对象，而 `bool(NoneType)` 是 True。
> **报错位置和真正原因完全不在一处。**

### 10-04 下午 · 生产数据库接通（Supabase）

**Supabase 项目建好并验证通过。**

| 项 | 结果 |
|---|---|
| 数据库连接 | ✅ 连接池 2.3 秒通，**20 张表自动建好** |
| 图片 bucket | ✅ `fridge-photos`（公开）已创建并双向验证 |
| `.env` | ✅ 三个值全部配好 |

**过程中挖出三个坑：**

**① Supabase 新版令牌默认「No access」。** 第一次给的令牌只有身份验证、
读不了任何东西（403）。必须手动勾 `Project → Read` 和 `Application services → Read`。

**② 本机网络按 SNI 拦截 `*.supabase.co`。** 诊断过程：

```
同一个 Cloudflare IP，只换 SNI：
  SNI = <项目>.supabase.co   ✗ 连接被重置
  SNI = api.supabase.com      ✓ TLSv1.3
  SNI = www.cloudflare.com    ✓ TLSv1.3
  www.google.com              ✗ 超时（说明是 GFW 级别，不是本机代理）
```

域名前置（换 SNI + 改 Host 头）被 Cloudflare 挡了（403）。

**影响很小**：数据库走 PostgreSQL 协议不受影响；只有 Storage 上传在本地失败，
按设计退回本地磁盘。服务器上没这个问题。

**③ 创建 bucket 的两条绕行路。** 管理 API 只有读 bucket 的接口、没有创建的。
于是：**直接往 `storage.buckets` 表插一行**（bucket 元数据就存这儿，
和 Storage API 内部做的事一样），再用管理 API 独立确认。
已写进 `docs/03`。

**另外一个提醒**：配好之后本地 `.env` 就指向生产库了，
**不能跑 `tests/test_e2e.py`** —— 它会注册几十个测试账号进去。

### 10-06 · 食材图库扩到 582 张，匹配能力大改

**Ethan 在外部程序生成了 574 张食材图**（12 个顶层分类、35 个子类，
带一份完整的清单 CSV）。这批图让食材配图从「40 张、大面积缺图」
变成「基本全覆盖」。

| | 之前 | 现在 |
|---|---|---|
| 食材图 | 40 张 | **582 张**（17MB） |
| 冰箱实测覆盖 | 24/37 | **34/37** |
| 匹配方式 | 手写关键词规则 | **词库 + 五级降级** |
| 分类 | 9 个 | **12 个**（和清单对齐） |

#### ① 图片导入

574 张 1024×1024 压到 512×512：**94.1MB → 14.7MB**（省 84%）。
给 `tools/import-images.py` 加了 `--src` 参数，可以直接指向外部目录，
不用先把图搬进 `.tmp-images-ingredients/`。

导入前**备份了原有的 40 张**（里面有 4 张是 Ethan 早先提供的真实照片）。

#### ② 从清单自动生成词库

574 条「中文名 → 图片 key → 分类」如果手写，等于把同一份数据抄第二遍，
改一处就会两边不一致。改成**生成**：

```
backend/data/ingredient-manifest.csv   ← 唯一数据源
        ↓ tools/build-ingredient-lexicon.py
backend/app/services/ingredient_lexicon.py   ← 自动生成，不要手改
```

#### ③ ⭐ 匹配改成五级降级（Ethan 提的核心需求）

他提的场景：**用户输「肥羊肉」，库里没有这个词，但要能理解是羊肉。**

| 级 | 依据 | 例子 |
|---|---|---|
| ① 挡刀区 | 手写规则，防加工品误配 | 番茄酱 → seasoning |
| ② 词库精确 | 574 条标准名 | 五花肉 → pork-belly |
| ③ 别名 | 手写高频俗称 | 车厘子 → cherry |
| ④ **词库子串** | 名字被包含，**最长优先** | **肥羊肉 → 羊肉** |
| ⑤ 关键词兜底 | 手写规则 | — |

实测：

```
肥羊肉 → lamb        内蒙古羔羊肉 → lamb     新鲜菠菜 → spinach
小番茄 → tomato      冷冻虾仁 → peeled-shrimp  澳洲牛排 → beef-steak
```

**最长优先**是关键：按名字长度倒序扫，第一次命中就是最长的那个。
所以「新鲜杏鲍菇」会命中「杏鲍菇」而不是「杏」。

> ⚠️ 子串匹配里**跳过了 1 字条目** —— 单字太容易误伤：
> 「梨」会命中「凤梨酥」、「杏」会命中「银杏」。单字只在精确匹配时生效。

#### ④ 顺带把分类扩到 12 个

原来 9 个分类塞不下清单的体系（清单有 63 条饮品、49 条零食），
硬塞会让「其他」变成杂物堆。改成和清单对齐的 12 个：

### 10-06 晚 · 注册加邮箱验证码（Ethan 发现的安全洞）

**Ethan 提出**：「我不确定是不是现在邮箱随便输入一个什么东西都能注册成功，
我要那种真实意义上的绑定，类似于需要发验证码的那种。」

**他判断得对。** 实测：

```
a@b.com                    → 201 注册成功 ✗
test@nowhere-xyz-12345.com → 201 注册成功 ✗
不是邮箱                    → 422（EmailStr 拦住了格式）
```

`EmailStr` 只校验**格式**，不验证邮箱是否真实存在 —— 邮箱那一栏形同虚设。

#### 做法

**SMTP 发信**（Python 标准库 `smtplib`，**不引入新依赖**）。
免费邮箱开个授权码就能用，比短信验证码便宜得多。

新增 `email_verifications` 表 + `app/services/email_service.py`
+ `POST /auth/send-code` 接口，注册接口增加必填的 `code` 字段。

#### 四道闸（接口是公开的，注册前还没有账号）

| 闸 | 值 | 防什么 |
|---|---|---|
| 同邮箱冷却 | 60 秒 | 连点「获取验证码」 |
| 同邮箱每日上限 | 10 次 | 把别人的邮箱当轰炸目标 |
| 验证码有效期 | 5 分钟 | 泄露后长期可用 |
| 最多尝试次数 | 5 次 | 暴力猜 6 位码 |

同一个邮箱发新码会**作废旧的**，避免同时存在多个有效码。

#### ⚠️ 不做账号枚举

**邮箱已注册时也返回成功**（只是不发码），响应结构和正常情况**完全一致**。
否则攻击者能拿这个公开接口批量探测「某个邮箱在不在这个平台上」。

> 这是个容易被忽略的点：功能上「告诉用户你已注册」是友好的，
> 但**在公开接口上区分这两种情况**就等于送了一个查询工具给攻击者。
> 真要提示，那句话应该发到邮箱里。

有测试钉住这一点（比对两种情况的响应结构）。

#### 其他取舍

- **验证码存 sha256 不存明文**，加邮箱当盐。故意**不用 bcrypt** ——
  6 位码本身防不住离线破解，真正的防线是「5 次上限 + 5 分钟过期」，
  用 sha256 是为了校验快（bcrypt 单次 100ms）。
- **邮箱统一转小写**存 —— 不转的话 `a@x.com` 和 `A@X.com` 会被当成
  两个不同目标，限流就绕过去了。
- **没配 SMTP 时不报错**，把验证码打到日志里（开发模式），
  启动时打一条显眼的警告。本地开发和自动化测试都能跑通。
- 注册失败返回 **400 而不是 401** —— 401 会触发客户端的
  「登录失效」处理，把用户直接踢回登录页。

**测试**：端到端 276 → **286 项**。取码从日志捞，**不做测试后门** ——
在生产代码里留一条「绕过验证码」的路径，风险远大于测试的便利。

#### 客户端同步改造

注册页加验证码输入框 + 「获取验证码」按钮（60 秒倒计时）。
不加的话客户端注册会直接 422。

四个细节：

- **倒计时秒数用服务端返回的**，不写死 60 —— 两边不一致的话，
  客户端倒计时结束了但服务端还在冷却，用户点了会莫名收到「发送太频繁」
- **发码按钮的 loading 和登录/注册的分开** —— 合成一个的话，
  点发码会让下面的「注册」按钮也变灰
- **切换登录/注册时取消倒计时** —— 不取消的话切回注册会看到莫名其妙的倒计时
- **成功提示和错误分开两个 Text** —— 合成一个的话，
  发码成功的提示会被下一次报错清掉

**真机实测跑通**：手机上点「获取验证码」→ 后端收到请求（来自 192.168.3.12）
→ 界面显示倒计时和开发模式提示。

#### 真机反馈后修的三个问题

Ethan 上手试了之后报了三件事：

**① 验证码明明是对的却提示「不正确」** ⚠️

查日志发现他**发了两次码**（13:55 拿到 `019031`，13:56 又拿到 `285824`），
然后用了先发的那一个 —— 而我原来的设计是「发新码就作废旧码」，
所以他手里的码已经失效了，而且错误提示只说「验证码不正确」，
他完全不知道为什么。

**修法**：**不再作废旧码**，旧码在有效期内继续可用。

> 安全性没有实质下降 —— 每个码都有 5 分钟有效期和 5 次尝试上限，
> 加上每天 10 次的发码上限，暴力破解窗口最多 50 次尝试，
> 而 6 位码有 100 万种可能。
> **宁可让「用户用旧码」也能成功，也不要让他对着一个正确的码反复被拒。**

同时把错误提示改成**告诉用户怎么办**：
「验证码不正确。如果你获取过多次验证码，请用最新收到的那一封」

**② 密码框里有一串自己没打过的圆点** ⚠️

不是 App 填的，是 **Android 密码管理器自动填充**的（截图里键盘上有个密码管理器图标）。
注册页被填上一个旧密码，用户会以为 App 有 bug。

**修法**：注册模式下给密码框加 `ContentType.NewPassword` 语义，
告诉系统的自动填充「这是**新**密码，别填旧的」。
登录模式不设 —— 那边自动填充是帮忙的。

顺带在切换登录/注册时**清空密码和验证码**：两者是不同的密码，
不清的话切过去会带着上一个，看起来就像「App 自己填了密码」。

**③ 密码框需要「小眼睛」**

加了显示/隐藏切换。**用文字按钮而不是图标** ——
项目里没引 `material-icons-extended`，为了一个眼睛去加依赖不值得
（这个项目的依赖矩阵很脆，加 Coil 3 触发过 Gradle 依赖图异常）。

**测试**：端到端 286 → **289 项**（新增：重复发码不作废旧码、
错误提示要说明怎么办）。

#### 邮箱服务接通（163）

QQ 邮箱卡了几轮之后换成 **163，一次就通**：

```
发信耗时 1.6 秒
接口返回「验证码已发送，请查收邮件」（不再是开发模式提示）
启动日志：邮箱验证码: 已配置（smtp.163.com）
```

**QQ 为什么不通**（记下来，以后少踩）：

1. **QQ 的授权码机制是「每次点生成，上一个立刻作废」** ——
   用户生成过多次的话，拿到手里的很可能是废码。
   163 的授权码是**常驻的**，生成一次一直有效。
2. **QQ 对连续重试很敏感** —— 短时间内多试几次就触发风控，
   之后报错在 `502` 和 `535` 之间轮换，**根本分不清是授权码错还是被限流**。
3. 调试时**原始 SMTP 对话**比 `smtplib.login()` 的报错清楚得多 ——
   手动发 `AUTH LOGIN` + base64，能看到「用户名被接受、密码被拒」，
   直接定位到是授权码问题而不是地址或网络。

> **教训：SMTP 认证失败不能像调 API 那样连着重试。**
> 失败一次就停下来，用原始对话看服务器原话，改完配置**等 10-15 分钟**再试一次。

**推荐顺序**：163 / 126 > QQ（QQ 的授权码机制更容易让人拿到废码）。

3. **替换代码块时容易吃掉函数的闭合括号** ——

### 10-06 深夜 · 性能优化：冰箱页 850ms → 169ms

Ethan 反馈「体验下来感觉很卡很慢」。

**根因：生产库在孟买。** 实测到 Supabase **单次往返 169ms**
（`SELECT 1` 和查真实表都是 169ms → 纯网络延迟，不是查询慢）。

而冰箱页要发 3 个请求，其中**两次是白花的**。

#### ① 读接口不再无条件写库（省 169ms）

`list_inventory` / `list_expiring` / `inventory_stats` 每次**读**都要
`db.commit()` 一次 —— 只为持久化「新鲜度」这个派生字段。
而 commit 是一次**完整的网络往返**。

绝大多数请求里新鲜度根本没变（今天没跨天），完全不需要写库。

改法：`refresh_freshness()` 返回「有没有真的变化」，只在变了才 commit。

> ⚠️ 不能用 `any(...)` 收集结果 —— 它会在第一个 True 处短路，
> 后面的食材就不会被刷新了。必须老老实实跑完整个循环。

#### ② 折叠箱列表合并成一次查询（省 169ms）

原来「查箱子 + 查成员」两次往返 → 合成一次 LEFT JOIN。

> ⚠️ 用 **outerjoin 不用 join** —— 空箱子也要返回。
> 用户刚建完还没放东西，inner join 会让它凭空消失。

#### ③ 客户端三个请求改成并发（省 680ms）

冰箱页要拉「分类顺序 + 折叠箱 + 食材列表」三样，原来**串行**发。
三者在服务端互不依赖，天然可以并发。

改法：`async {}` 三个一起发；**先 await 食材列表**（用户真正在等的），
分类顺序和折叠箱到了再更新界面，不阻塞内容显示。

#### 效果

| | 之前 | 现在 |
|---|---|---|
| `/inventory` | 342ms | **169ms** |
| `/food-categories` | 338ms | **169ms** |
| 客户端总耗时 | 串行 849ms | **并发 169ms** |

**约 5 倍。**

#### ⚠️ 一条通用教训：远程数据库的「读」不要顺手写

每次 commit 都是一次网络往返。**在本地 SQLite 上完全感觉不到**，
换成远程库之后，一个多余的 commit 就是用户能感知到的卡顿。

**判断标准**：这个写操作是「业务需要」还是「顺手持久化派生字段」？
后者应该只在真的变化时才做。

> 孟买这个区域当初是建项目时选的（我建议的是新加坡）。
> 改区域要重建项目 + 迁移数据，代价大，先用代码层面优化扛过去。

#### 顺手加了个搜索框

89 条一屏一屏滑就不合适了。搜索框**固定在顶部**（不跟着列表滚）——
滚到一半想换个词搜还要滑回顶部很烦。

**为什么在客户端过滤，不发给后端**：89 条的标题 + 摘要只有几十 KB，
**已经全在内存里了**。本地过滤即时、不依赖网络；发给后端要多等一次往返
（生产库在孟买，单次约 169ms），输入框会明显发顿。
而且过滤**没有加防抖** —— 纯内存过滤是微秒级，加防抖反而让输入和结果不同步。
（如果以后涨到几千条再考虑后端搜索。）

**没结果时区分两种情况**：是搜不到，还是被分类筛选筛掉了？

不区分的话用户会以为「这个应用里没有这条」。

#### ⚠️ 踩的坑：拿半角引号当中文引号

写内容时习惯性用了 `"文字"`，Python 把它当字符串结束符，
直接 `SyntaxError`。**踩了两次**（第一次修完还有漏网的）。

> 教训：这个项目里中文内容一律用 **「」**。
> 半角 `"` 只允许出现在语法位置（key、值的外框）。
> 修的时候别用关键词扫一遍就以为干净了——
> 第二次是在别的位置又冒出来一个。

#### 新增 `tests/test_food_tips.py`（29 项）

内容库也要测。手写内容最容易出的是**不报错但不对**的问题：

- `id` 重复 → 详情页永远只打开其中一条，另一条**访问不到**（不报错）
- `category` 写错一个字 → 那个分类筛选里**少一条**（没人会发现）
- `source` 漏填 → 内容失去可信度依据，而这是这类内容**唯一的底线**
- `summary` 太长 → 客户端列表页换行错乱

这些都不会让服务起不来，只会静默地少一点东西，所以用断言钉住。

**断言的分寸**：只测**结构性**的东西（字段、枚举、长度范围），
**不测内容对不对** —— 「螃蟹和西红柿能不能同吃」的对错靠 source 里
引用的权威来源保证，机器判断不了。

写这个测试时自己踩了两个「断言写太死」的坑，都改掉了：
① `source` 只认机构名关键词，把
「Miranda & Schaffner, Applied and Environmental Microbiology, 2016」
这种正经文献引用误判成不合格 → 改成「有年份 / 有书名号 / 有机构关键词」三选一；
② 「谣言条目必须解释原因」用关键词判失败，产生假警报
→ 改成**只提醒不判失败**（因为「讲清原因」的写法太多样，有的甚至是正面立论）。

### 10-06 · 折叠箱终于能管了（真机 5 条链路全部验收）

#### 顺手修掉的两个问题

**① 冰箱为空时，整个列表不渲染 → 折叠箱入口消失**

原来的条件是 `state.items.isEmpty() -> EmptyState(...)`，
意思是「食材列表为空就显示整页空状态」。但折叠箱的管理入口在
**那个 LazyColumn 里面**，所以：

- 搜索关键词没匹配到任何食材 → 想顺手改个箱子，发现入口没了
- 冰箱真的空但建过箱子 → 连删都删不掉

改成 `state.items.isEmpty() && state.boxes.isEmpty()`：
只有「真空 + 没箱子」才给整页空状态。

**② 折叠箱里的食材行被折成 5 行**

`FridgeItemRow` 右侧用 `IconButton`（**48dp 最小尺寸**）。
折叠箱里一行有三个动作（移出 / 改 / 删）= 144dp，
加上 52dp 的图和新鲜度标签，食材名那一列只剩不到 40dp。
实测长这样：

```

个
```

#### 接着补上排序（同一类「做了一半」）

折叠箱的 `sort_order` **后端一直支持**（`PATCH` 里就有这个字段），
但客户端完全没用 —— 和「管理界面没接」是同一个毛病。
这次一起补掉。

**后端加了一个新接口 `PUT /food-categories/order`**，
而不是复用单条 `PATCH`：

| | 单条 PATCH 挪一格 | 整批 PUT（选了它） |
|---|---|---|
| 服务端要知道当前顺序 | **要**（得先读一次） | 不用 |
| 两次操作之间 | 有窗口，两设备同时挪会互相覆盖 | **幂等**，后到的赢 |
| 请求数 | 2 次（交换两个值） | **1 次** |

⚠️ **不在列表里的箱子不动它们**（保持原 `sort_order`）。
客户端可能只拿到一部分，如果按「传进来的才有效」把其余的也重排，
它们会莫名其妙跑到最前面。

**客户端用乐观更新**（和新建/删除相反）。理由写进注释了：
增删实体乐观更新会「闪一下」，比等回包更糟；而排序是**纯顺序变化**，
乐观更新只是把两行换个位置，视觉平滑。而且每次发的都是完整顺序，
**幂等**，所以不用 `boxBusy` 挡连点 —— 挡了反而会丢操作。

**真机验收**（3 个箱子，`sort_order` 全为 0 起步）：

```
初始（按创建顺序）：AAA 火锅材料 / BBB 早餐 / CCC 给猫的
AAA「下移」→      BBB 早餐 / AAA 火锅材料 / CCC 给猫的
  数据库：BBB=0  AAA=1  CCC=2        PUT /food-categories/order → 200
AAA「上移」→      AAA 火锅材料 / BBB 早餐 / CCC 给猫的
  数据库：AAA=0  BBB=1  CCC=2
重启 App 顺序保持 ✓
```

「上移 / 下移」在**到头时显示为禁用**而不是藏起来 ——
藏起来用户会以为「这个箱子不能排序」，实际是「已经是最上面了」。

**测试**：`test_e2e.py` 新增 9 条断言（含「整批」「幂等」
「不可见的 id 静默跳过」「全不可见 → 400」「空列表 → 422」）。
**322 项端到端全过。**

### 10-06 · 部署从「1-2 小时手工」变成「一条命令」

B 线（云上部署）一直卡在等服务器。但**部署本身是可以先做掉的** ——
`docs/03` 里那套手工步骤有 6 大步、十几条命令，中间要改 3 个配置文件，
每一处都能写错（缩进、路径、端口、`server_name`），报错还都很晦涩。

**新增 `tools/deploy.sh`**，服务器到手后：

```bash
scp tools/deploy.sh root@你的服务器IP:~/
bash deploy.sh 1.2.3.4.nip.io        # 没域名就用 nip.io
```

一条命令做完：装依赖 → 建 `fridge` 用户 → 拉代码 → 建虚拟环境 →
生成 `.env` → 跑测试 → 配 systemd → 配 Nginx → 上 HTTPS →
配 Supabase 保活 cron → 自检。

**几个刻意的设计：**

| 决定 | 为什么 |
|---|---|
| **可重入** | 中途失败（比如要先去 Supabase 控制台拿连接串）修好后**再跑一次**就行，做过的步骤跳过。这比「一次成功」现实得多 |
| **不用 root 跑服务** | systemd 里 `User=fridge`。root 跑的话服务被攻破 = 整台机器失守 |
| **uvicorn 只监听 127.0.0.1** | 外部流量一律走 Nginx。监听 `0.0.0.0` 会绕过 HTTPS，以后要加的限流也一起绕过 |
| **`.env` 权限 600** | 里面有密钥，只给 `fridge` 读 |
| **密钥现生成** | 不沿用开发环境那份 `SECRET_KEY` |
| **worker 数按核数，封顶 4** | 文档里写死 2 是因为那是 2 核机器。核数更多就多开，但再多人也没用（瓶颈在 AI 和数据库往返），只是白吃内存 |
| **certbot 失败不中断** | 证书签不下来通常是域名 A 记录还没生效，这时候 HTTP 仍然能用。警告 + 告诉你怎么单独补签，比整个脚本挂掉好 |
| **结尾自检** | 把「连的是 Supabase 还是 SQLite」「图片存 Supabase 还是本地」直接打出来 —— 这两个是部署时最容易搞错、又最不容易发现的地方 |

#### ⚠️ 没法端到端验证，所以把纯逻辑抽出来自测

本地没有 Docker，WSL 被安全策略挡住 —— **装包 / systemd / Nginx /
certbot 那几步我一次都没跑过**。这一点必须说清楚，不能假装验证过了。

能做的是把**最容易静默出错**的纯逻辑抽成函数，配一个自测模式：

```bash
bash deploy.sh --selftest     # 12 项，不需要 root，不碰系统
```

覆盖两块：

1. **连接串规范化**（`postgresql://` → `postgresql+psycopg://`、
   补 `?sslmode=require`）。这块写错的表现是「有时候连得上、有时候连不上」
   —— psycopg 默认 `prefer`，SSL 失败会退回明文，而 Supabase 拒绝明文。
   排查起来极其痛苦，所以钉死它。
2. **worker 数计算**（封顶 4）。

写自测时立刻抓到一处逻辑错：我原来给**任何**非空连接串都补 `sslmode`，
包括 `sqlite:///x.db` —— sqlite 不认这个参数，启动时才报错。
改成只处理 `postgresql://` / `postgresql+psycopg://`，其余原样返回。

> **结论：没法端到端验证的脚本，至少把纯逻辑抽出来自测，
> 并在文档里明说哪部分没验证。** 这比「看起来很完整」诚实，也更安全。

#### 顺手修掉文档里几处过时的数字

- `docs/03` 里「251 项测试」→ **322 项**；「11 张表」→ **21 张**
- `docs/03` 里「跑测试会污染 Supabase、要按邮箱前缀清理」→ **已作废**。
  测试现在在导入 app 之前就把 `DATABASE_URL` 指向临时 SQLite，
  并把 AI Key 和 SMTP 都置空，随时可以跑
- `docs/00` 里 4 处「251 项」→ 322 项；B3 那节改成「先跑脚本」

### 10-06 · 菜品库 192 道菜的做法**全部预写进数据库**（点开不再调 AI）

Ethan 的原话：

> 「我不要这种每次点开都 ai 现场生成的，我要那种本来就现成的，
>   根据食材生成出来的菜谱是数据库里有的，
>   扩充了这么多的菜品都要在数据库里写好热量做法等等」

之前 `materialize` 是「点开才让 AI 现写」，第一次点要等 **8.7 秒**。
现在改成：**离线生成一次 → 存进数据库 → 点开是查库返回**。

#### 一、离线生成 192 道菜的做法

新增 `tools/generate-dish-recipes.py`：复用现有的
`generate_recipes(focus_dish=菜名)`（那条提示词已经调好了），
用**菜品自身的必需食材**拼一个合成库存当上下文
（`generate_recipes` 见空库存会直接返回空列表）。

```
菜品库共 192 道，本次要生成 190 道
[  1/190] 上汤娃娃菜   ✓ 6 步  10.6s   预计还要 33 分钟
...
[190/190] 龟苓膏      ✓ 5 步   9.3s
成功 190 道，失败 0 道，用时 33.7 分钟
```

产出 `backend/data/dish-recipes.json`（**进 Git**）——
存 JSON 而不是直接写库，是为了能复核、能 diff、能重跑单道。
**每生成一道就写一次盘**，中途断了可以重跑续上。

#### 二、写进数据库：用 `user_id = NULL` 表示「系统内置」

`recipes.user_id` 的注释里本来就写着「NULL 表示系统内置菜谱，所有用户可见」——
**字段早就留好了，但查询里从来没算进去**（所有地方都是
`Recipe.user_id.in_(visible_user_ids(...))`，NULL 匹配不上）。

新增 `tools/seed-dish-recipes.py` 把 192 道以 `user_id=NULL, source='builtin'`
幂等 upsert 进去。这样**一份记录所有用户共用** —— 包括评委新注册的账号，
不用为每个用户各存一份，也不用调 AI。

#### 三、⚠️ 读和写的可见范围必须分开

这是这次最容易出事故的地方：

| | 范围 | 用在哪 |
|---|---|---|
| `readable_recipe_clause` | 系统内置 + 自己/家人 | 列表、详情、做菜预览、扣库存、采购清单、行为上报、广场分享 |
| `editable_recipe_clause` | 自己/家人（**不含内置**） | 按菜名查重、删除 |

**不分开的后果**：用户能**删掉系统内置菜谱** —— 那是所有用户共用的一条记录，
删一次全都没了。所以删除走 `editable`，而且内置的给 **403 而不是 404**
（用户明明看得见详情页，说「不存在」是自相矛盾的）。

同理，AI 生成时按菜名查重也必须是 `editable` —— 否则用户生成一道同名菜，
会把**全局那条**改写成他自己的版本（`source` 从 builtin 变成 ai），
等于一个人污染了所有人的菜品库。

#### 四、⚠️⚠️ 性能：74 秒 → 12 毫秒（两个独立的坑）

改完之后「菜谱列表」慢到 **74 秒**。查下来是两个叠加的问题：

**① `commit()` 让对象过期 → N+1 懒加载**

`_load_inventory` 里有个 `db.commit()`（刷新鲜度用），而 SQLAlchemy 的
commit **默认会让 session 里所有已加载对象过期**，之后每访问一个字段
都会触发一次 SELECT。列表是先查菜谱、再取库存，于是 200 道菜
每个字段一次查询 —— **200 × 169ms（Supabase 孟买往返）= 34 秒**。

修法两条：
- `_load_inventory` **没变化就不 commit**（绝大多数请求都属此类）
- 调用方**先取库存、再查菜谱**，让 commit 发生在菜谱被加载之前

**② 数据量本身**：192 道完整菜谱是 **482KB**，从孟买拉回来 4 秒。
（整个接口只有 5 条 SQL，瓶颈是字节数不是往返次数。）

**所以「把菜品库塞进『全部』列表」这个方案被否掉了** ——
菜谱页是主 tab，进去卡 4 秒不可接受。菜品库的浏览入口是**「推荐」标签**
（按冰箱里现有的食材挑），点推荐卡才走 `materialize` 拿这一道。
真要浏览全部 192 道，得单独做个标签页 + 列表不返回 steps/ingredients
（能省 75% 体积）+ 分页 —— 那是另一件事。

顺带把 `visible_user_ids` 加了 per-session 缓存：它在**同一个请求里会被调
好几次**（算可见范围一次、取库存又一次），每次 169ms。
缓存挂在 `db.info` 上，生命周期正好是一个请求。

**结果**：`materialize` 从 8.7 秒（AI）降到 **约 960ms**（查库，4 条 SQL）。
剩下的全是到孟买的网络往返 —— 服务器部署到香港后会更快。

#### 五、⚠️ 又一个只在 Postgres 上才炸的坑

灌库时报 `StringDataRightTruncation: value too long for type character varying(16)`。

模型偶尔在 `unit` 字段里塞注释，实测出现过的脏值：

```
「汤匙（即oyster-sauce）」   17 个字 —— 直接超长
「个（可选）」「茶匙（可选）」  把 optional 混进了单位
「/2勺」「/4 茶匙」          分数写残了，前面的 1 丢了
```

`recipe_ingredients.unit` 是 `VARCHAR(16)`，而 **SQLite 不校验长度**，
所以本地测试全过、只有生产库会炸 —— 而且它出现在**写库**路径上，
等于「AI 哪次心情不好，用户就存不了菜谱」。

修法：`recipe_service.clean_unit()`，**写库的两个入口共用**
（`_persist` 和种子脚本）：去括号注释 → 去残缺分数的前导斜杠 →
还是空的或超长就退成 `份`（兜底而不是截断 —— 截断只会得到
「汤匙（即oyster-sa」这种更莫名其妙的值）。

#### 六、顺手修掉的连带问题

- **广场分享**：原来只允许分享「自己的菜谱」（`Recipe.user_id == user.id`）。
  菜品库变成内置菜谱之后，发帖界面能选到它们、提交却报
  「找不到这道菜（只能分享自己的菜谱）」—— 用户会觉得「你明明让我选的」。
  改成 `readable`，并顺手改了报错文案。
- **采购清单**：同理，从菜品库点开一道菜再点「把缺的加进采购清单」
  会报 400「还没有可用的菜谱」。
- **加了 GZip 中间件**：JSON 压缩 70-85%，实测 19602 → 7265 字节（省 63%）。
  `minimum_size=1000` 是故意的 —— 小响应压缩后反而更大。

#### 真机验收（小米 15 Ultra）

```
菜谱页 →「推荐」→ 点「三杯鸡」
  → 约 1 秒跳转菜谱详情
  → 专属配图 / 35 分钟 / 中等 / 高蛋白·增肌
  → 需要什么：共 9 样（鸡腿肉 500g 缺、酱油 3汤匙 ✓、米酒 3汤匙 缺…）
  → 5 步做法 + 营养估算（480 千卡 / 蛋白质 42g / 钠 950mg）+ 免责声明
  → 把缺的 5 样加进采购清单
「全部」标签 → 只有用户自己生成的菜谱（带「删除」），没有内置的 ✓
```

**测试**：`test_e2e.py` 新增 16 条断言（见「6c2. 系统内置菜谱」）——
跨用户可见、删除被拒 403、materialize 不新增行、全局记录不被改写、
能按内置菜谱建采购清单、能分享到广场。**338 项全过。**

#### ⚠️ 排查过程中的一个弯路

真机上 App 退回登录页，第一反应是「后端地址不对 / 后端挂了」。
实际查下来是：**手机 Wi-Fi 被关了**，跑在移动数据上（`ip addr` 里
只有 `rmnet_data1`，`dumpsys wifi` 说 `Wi-Fi is disabled`）。
ping 局域网 IP 居然还能通（44ms —— 局域网正常应该 <5ms，这个延迟本身就是线索），
但端口是 `Connection refused`。

> **线索：ping 通但端口 refused，而且 ping 延迟异常高 → 先查手机在哪个网络。**

### 10-06 · 给百炼额度上一道保险（AI 每日配额）

**起因**：后端的接口**原本没有任何限流**，而注册是开放的 ——
理论上任何人发现域名后注册个账号，就能反复调 `/vision/scan` 和
`/recipes/generate`，**每一次都在花项目自己的钱**
（`qwen-vl-max` 识别一张图约 2 分钱）。

对学生参赛项目来说，「被人刷掉几十块」不是理论风险。

#### 两道闸，缺一不可

| 层 | 作用 | 默认 |
|---|---|---|
| **按用户** | 防单个账号霸占额度 | 30 次/天 |
| **全站** | **给账单兜底** | 500 次/天 |

**只有按用户限流是不够的** —— 攻击者注册 100 个账号就拿到 100 倍额度。
全站那条才是真正的「最多花多少钱」。

新增 `ai_usage` 表（复合主键 `day + user_id`）+ `services/quota_service.py`，
在 `deps.py` 里统一成 `guard_ai_quota(db, user_id)`，
调 AI 的三个地方各加一行：`/vision/scan`、`/recipes/generate`、
以及 `/recipes/materialize` 的 **AI 兜底分支**。

#### 几个刻意的决定

| 决定 | 为什么 |
|---|---|
| **配额落库，不放内存** | 放内存的话每个 uvicorn worker 各算各的（实际额度 = 配置 × worker 数），重启还会清零。代价是每次 AI 调用多约 700ms —— 但 AI 本身要 2.6~20 秒，这点开销可以忽略；而**配额不准就等于没有配额** |
| **`materialize` 只在兜底分支扣** | 正常情况它是查库返回（不花钱）。放在函数开头会让每次点推荐菜都白扣一次 —— 而那本该是免费的 |
| **放在参数校验之后** | 图片格式不对的请求不该白扣一次配额 |
| **返回 429 + `Retry-After`** | 429 是标准语义，客户端能据此区分「没权限」和「用超了」 |
| **429 文案里给替代方案** | 「额度用完了」很绝望；补一句「可以先点『推荐』标签，那里不调 AI」就有出路了 |
| **`user_id = -1` 表示全站** | 用 NULL 更自然，但 `(user_id, day)` 的唯一约束在 **PostgreSQL 里对 NULL 失效**（NULL 互不相等），能插出无数行 |

#### 已知的并发缺口（故意不修）

「先读再写」不是原子的：两个并发请求可能同时读到 `count = 29`，
于是都放行，实际变成 31 次。

**这个偏差是故意的** —— 要修就得加行锁或原子 upsert，
那会让每次 AI 调用再多一次往返和一把锁。对一个「防滥用」而不是
「精确计费」的场景，多放行一两次完全可接受。

#### 验证

- **e2e 新增 13 条断言**（第 17e 节）：额度内放行 / 超出 429 /
  文案含替代方案 / 带 `Retry-After` / 全站闸也生效 /
  **额度为 0 时推荐·列表·冰箱·小贴士仍然可用**
  （不调 AI 的接口不该被拦 —— 否则「额度用完 = App 不能用」，
   那是把限流做成了自残）
- 另外在 6c2 节断言了**「额度为 0 时 materialize 仍能返回内置菜谱」**，
  这条钉住了整个设计的意义：点推荐菜是查库，不该花额度
- **生产库实测**：`/vision/status` 返回 `ai_quota_left: 30` →
  调一次 `/recipes/generate` → 变成 `29`，
  `ai_usage` 表里 `user=1` 和「全站」各 1 条 ✓

**测试**：e2e **351 项**（+13）全过。

`deploy.sh` 生成的 `.env` 里也带上了这两个配置项，
演示前怕被限住就调大 `DAILY_AI_LIMIT_PER_USER`（不用改代码）。

### 10-06 · 扫描页显示「今日还剩 N 次 AI 识别」

后端上一轮加了每日配额，但**客户端一个字都没显示** ——
用户被 429 拦下来时才第一次知道有「额度」这回事，
感受就是「昨天还好好的，怎么突然不行了」。

或者看看『推荐』菜谱」。

#### 一个容易写错的细节：默认值必须是 -1 而不是 0

`aiQuotaLeft` 的默认值取 `-1`，表示「**还不知道**」（状态接口失败 / 后端版本旧）。

如果图省事写成 `0`，那么**状态接口一失败就会把拍照按钮灰掉** ——
把网络问题显示成了额度问题，用户会以为今天不能用了。

界面逻辑相应是 `quotaLeft == 0`（真的用完）才禁用，
`quotaLeft < 0`（不知道）**什么都不显示** ——
显示「还剩 -1 次」比不显示更糟。

#### ⚠️ 这次**没有在真机上验证**

改动做完时手机锁屏了，而且需要 PIN —— **我没有去绕**（那是别人的手机）。

客户端配了 `ignoreUnknownKeys`，后端加字段不会解析失败；
但如果后端写 `ai_quota_left`、客户端漏了 `@SerialName`，
解析出来就是默认值，**不报错但功能静默失效**。

5 个用例：

| 用例 | 钉住什么 |
|---|---|

| `status_parsesLowQuotaFlag` | `ai_quota_low` 能解析 |

### 10-06 · 生成菜谱改成查库（不调 AI）+ 图片配对核查 + 流畅度优化

Ethan 一次提了四件事，逐条对应。

#### 一、`/recipes/generate` 不再调 AI —— 改成关键词匹配

原话：

> 「生成菜谱我觉得不需要调用 ai，做一个类似于关键词提取器的内容，
>   因为数据库里有的菜品都会写需要什么食材，那么既然如此，
>   当用户冰箱里有的时候，生成的菜就可以直接是包含这个食材的」

**完全正确。** 菜品库里每道菜都标了必需食材，这件事**查表就能算**，
没有任何需要「理解」的东西。用 AI 的代价是：约 20 秒、每次花钱、
同样的冰箱给的菜还不一样（温度 > 0）。

改成查库之后：**毫秒级、免费、结果稳定可复现**。

| | 改前 | 改后 |
|---|---|---|
| 耗时 | 约 20 秒 | **毫秒级** |
| 成本 | 每次调 AI | **0** |
| 扣配额 | 扣 1 次 | **不扣** |
| 结果 | 每次可能不同 | 同冰箱同结果 |

**AI 现在只用在拍照识别上** —— 那才是真正需要视觉理解的地方。

几个细节：
- **只看 `ready`**（必需食材齐全）—— 这个接口给的是「你现在就能做的菜」
- **已有的菜不再重复挑**，所以连点几次是「每次都挑新的」
- 落库时 `source="library"`（不是 `ai`），留着以后排查用
- `save=true` 的权限检查**提到最前面**：放在「有没有挑到菜」之后的话，
  只读成员在冰箱空时会拿到 200 —— 权限判断不该依赖数据状态

#### 二、192 道菜的配图逐张核查：**只有 1 处错**

做法：把 192 张图连菜名做成 8 张带标签的拼图（`outputs/dish-image-pairing-*.jpg`），
逐张看了一遍。

**结论：191/192 正确，1 处错配 ——「地三鲜」。**
它的图是**小白菜 + 胡萝卜 + 蘑菇**，而地三鲜应该是土豆 + 茄子 + 青椒。
（这是外部生图时提示词跑偏了，不是配对逻辑的问题 ——
key 和文件名的对应关系 192/192 全对。）

> 另外两个一开始看着可疑、复核后确认是**对的**：
> 「炒豆芽」在缩略图里像面条（其实是豆芽堆）、
> 「回锅肉」的图是蒜苗 + 肉（那是经典的蒜苗回锅肉）。
> **教训：缩略图会骗人，可疑的要单独放大看。**

#### 三、采购项变暗响应慢 —— 改成乐观更新

**根因**：点「买好了，写回冰箱」之后，原来的流程是
「等服务器写完库存 → 再 `load()` 拉一次全量 → 卡片才变暗」。

而写回冰箱是**逐条**改库存（每条还要跨家庭查同名合并），
生产库在孟买一次往返 169ms —— 10 项就是一两秒。
用户看到的是：点了按钮、转圈、一两秒后界面才动。

**改成**：
1. 立刻把勾选的条目标成「已入库」、整单标成完成（**变暗**）
2. 再发请求
3. 成功 → 用**服务端返回的那份**替换本地（省掉一次多余的 `load()`）
4. 失败 → 报错 + 重新加载（回滚）

顺手去掉了一个 `notify(SHOPPING)` —— 本 ViewModel 就订阅了那个 topic，
那等于自己触发一次全量 reload，白多一次往返。

> ⚠️ 「整单完成」的判定规则要和后端一致（后端是
> `if all(i.checked ...)`）。规则改了这里也要改，否则会出现
> 「界面变暗了但服务器还是 pending」，下次刷新又弹回来。

#### 四、流畅度：三处串行请求 + 静态图没有缓存头

**① 首页三个请求是串行的 → 改成并发**

```kotlin
// 改前（3 × 169ms ≈ 510ms）
val statsResult = inventoryRepository.stats()
val listResult = inventoryRepository.list()
val expiringResult = inventoryRepository.expiring(3)
```
生产库在孟买单次往返 169ms，串行就是白多花两次往返。
改成 `async` 并发后 **510ms → ~170ms**。
首页是打开 App 的第一屏，这 340ms 用户能明显感觉到。

同样的毛病还在**采购页**和**个人页**（各 2 个串行请求），一起改了。

**② ⭐ 静态图片没有 `Cache-Control`（这条影响最大）**

从后端日志里数出来的：打开冰箱页触发 **35 个食材图请求**，
菜谱页的推荐列表再触发 **40 多个菜谱图请求**，**全是 304**。

根因：FastAPI 的 `StaticFiles` 只发 `etag` / `last-modified`，
**不发 `Cache-Control`**。而客户端拿到没有 `Cache-Control` 的响应时，
**每次都要回来问一遍**「这个还能用吗」—— 每次都是一个完整的条件请求。

修法：`CachedStaticFiles`（`StaticFiles` 的子类）加上
`Cache-Control: public, max-age=86400`。

**为什么是 1 天而不是 7 天**：图片按 key 命名，重新生成时文件名不变 ——
缓存太久用户会一直看到旧图。1 天是个平衡。
（nginx 那边也配了 `expires 7d`；两边都配是因为开发环境没有 nginx，
只配一边的话本地开发体验比线上还差。）

**测试**：e2e **360 项**（改写了「生成菜谱」「做菜扣库存」几节，
新增「不调 AI」「每次都挑新的」「配额用完时生成仍可用」等断言），
匹配 161、分类 99、贴士 29；Android 单测 20 项。**全过。**

改完准备装包时手机被拔了（`adb devices` 为空）。

```
① 甜的      黄桃/菠萝/什锦/山楂/梨罐头…            → canned-fruit
② 荤的      午餐肉/金枪鱼/豆豉鲮鱼/鱼罐头…          → canned-meat
③ 词库里有的 水果罐头 / 肉食罐头                    → 显式列出（否则被兜底抢走）
④ 不甜不荤的 玉米/蘑菇/番茄/八宝粥/芦笋/蔬菜罐头      → 各自更贴切的原料图
⑤ 兜底      罐头                                  → canned-fruit
```

⑤ 兜到水果罐而不是肉食罐：日常说法里「罐头」不加限定词时更多指甜口的
（咸口的通常会说「午餐肉」「鱼罐头」）。想换成一罐午餐肉的话，
把 `(("罐头",), "canned-fruit")` 的值改掉就行。

#### 顺手修掉同类问题：泛称词也会退到香菇红枣

排查时系统扫了一遍泛称词，发现**同一类洞**还有 5 个：
「主食」「零食」「调料」「豆制品」「咸菜」都解析不出来 → 全退到香菇红枣。
而它们明明**各自都有对应的万能图**（`_universal-staple` 等）。

> ⚠️ 加子串规则要小心抢词：「主食」会把「主食面包」抢走

> 加完用「词库里有没有条目被挡刀规则抢走」那条断言验一遍（已有的，直接跑）。

#### ⚠️ 排查中发现的真问题：**端口 8000 上有两个后端在跑**

改完之后接口还是返回香菇红枣，但直接 import 同一个模块算出来是对的 ——
**说明跑着的进程用的不是新代码。**

查下来：`netstat` 显示 8000 端口有**两个** LISTENING，
一个是我刚起的（PID 21644），另一个是 10:36 启动的旧进程。
而且旧进程在 `netstat` 里显示的 PID（21156）**根本不存在** ——
它的监听套接字被子进程（PID 8012）继承了，
所以按 PID 杀杀不到，请求还全被旧进程接走。

> **教训（部署时会再遇到）**：
> 1. `run.py` 用的是 uvicorn **reload 模式** → 父进程 + 子进程两个 python.exe，
>    只杀占端口的那个，父进程会把旧的拉回来
> 2. Windows 上**两个进程可以同时 bind 同一个端口**（SO_REUSEADDR），
>    所以「新后端起来了」不代表它在接请求 —— **必须看 netstat 有几个 LISTENING**
> 3. 重启后端要按**命令行**找进程（`CommandLine -like '*run.py*'`），
>    把父子一起停干净；`Stop-Process` 有效，`taskkill` 在沙箱里会静默失败

#### 两个校验测试要放宽

新规则指向 `_universal-*`（分类万能图），触发了两条原有的校验：

| 测试 | 原来的限制 | 放宽成 |
|---|---|---|
| `test_ingredient_rules` 6b | 规则的值必须匹配 `[a-z0-9-]+` | 允许开头一个下划线（`_universal-*` 是真实存在的图） |
| `test_ingredient_category` 1 | 规则表里每个 key 都要标分类 | 排除 `_universal-*`（它**本身就是分类的代表图**，标分类等于自己指向自己） |

（原来只查了别名表，挡刀区没查 —— 而挡刀区一旦指向不存在的 key，
那一整批词全都会静默退到万能图）。

### 10-07 · 部署前预演：**数据库连接数会不够**（会让部署直接崩）

服务器还没到手，所以先把 `tools/deploy.sh` 按这两天的改动过了一遍。
翻到连接池配置时顺手实测了一下 —— **发现一个必然踩的坑**。

#### 实测结果

```
连接串: aws-0-ap-south-1.pooler.supabase.com:5432/postgres
  第 11 条失败: OperationalError: FATAL: (EMAXCONNSESSION) max clients reached
最多同时开 10 条连接
```

**Supabase 的连接池只允许 10 条并发连接。**

#### 而原来的配置需要 20 条

`session.py` 里是 `pool_size=5, max_overflow=5` = **每个 worker 10 条**，
注释还写着「两个 worker 一共 20 条，留出余量」——
**20 > 10，一个 worker 就把额度吃满了**，第二个 worker 一并发就报错。
`deploy.sh` 的 `pick_workers` 还封顶 4 个 worker（要 40 条）。

这个错**只在并发高的时候才冒出来** —— 也就是**演示当天有人一起用的时候**，
而且报错是「连不上数据库」，完全看不出是连接数的问题。

#### 修法

| 改哪 | 原来 | 改成 |
|---|---|---|
| `session.py` | `5 + 5 = 10`/worker | **`2 + 2 = 4`/worker** |
| `deploy.sh` `pick_workers` | 封顶 4 | **封顶 2**（4 × 2 = 8 ≤ 10，留 2 条余量） |
| `deploy.sh` | 无 | **新增一步「自检：数据库连接预算」** |

新增的自检会按当前 worker 数**主动开满连接试一次**，开不满就在部署阶段
报出来（而不是等演示当天），并提示两个常见原因：本机后端还占着、
或者上限比预期低。

`pick_workers` 的自测也补了连接预算断言：
`1/2/4/8/16 核 → worker 数 × 4 ≤ 10`。

#### ⚠️ 这个额度是**整个项目共享**的

本机开发的后端和服务器上的后端抢同一份 10 条。
所以**部署前要把本机的后端停掉** —— 否则服务器会随机报「连不上数据库」，
看起来像 Supabase 挂了，其实是本机占着。

（这也是今天排查「罐头图不更新」时那个僵尸进程的另一层危害：
它不光用旧代码接请求，还一直占着 4~10 条连接。）

#### 顺带修正的文档

- `session.py` 里那句错误的「20 条，留出余量」改掉了，写清实测的 10 条上限
- `docs/03-部署到公网.md` 补了「worker 数受连接数限制」的表格和公式：
  `(pool_size + max_overflow) × worker ≤ 10`

**测试**：e2e 360、匹配 182、分类 99、贴士 29、`deploy.sh --selftest` **17** 项。
全过。新配置下本机后端实测正常（6 个并发请求全 200）。

#### 我**不建议**继续加规则，理由

其中大概 25 个（水产 / 谷物 / 佐料 / 点心 / 饮品 / 时蔬…）确实能对上现成的万能图，
再加 25 条规则就能修掉。**但那是治标：**

真正的根因是 —— **`_universal-other.jpg` 这张「其他」万能图，
画的是一堆很具体的东西（香菇 + 红枣）**。
它被当成「兜底」用，可任何东西兜到它都显得配错了。
只要还有「我没预料到的词」，它就还会以同样的方式出错 ——
加规则是打地鼠，永远打不完。

#### 两个真正的修法（都要 Ethan 拍板）

| 方案 | 代价 | 效果 |
|---|---|---|
| **A. 重生成 `_universal-other`**，换成**真正通用**的图（比如一只装杂货的纸袋、一篮什锦食材） | **要花积分**（一张图） | **一次修掉全部 42 个**，以后新增的未知词也不会再显得配错 |
| **B. 认不出来的词**干脆**不返回图**（返回 `None`），让客户端显示「首字 + 色块」占位 | 免费 | 占位图看着是「没配图」而不是「配错了」；但失去了「至少给张照片」的兜底 |

我倾向 **A**：一张图换掉一整个类别的错，而且通用图本来就不该画具体食材。
B 也不坏，但它把「缺图」和「配错图」的取舍反过来了 ——
代码里当初选「给张图」是因为「有图总比占位好看」，
那是在**图本身通用**的前提下才成立。

> 现状：这 42 个词**只在用户真录进这种泛称时才出现**，
> 日常用词（西红柿、鸡蛋、猪肉…）都不受影响。
> 所以**不阻塞部署**，可以部署完再决定。

## 更新约定

**每次做完一次优化，往「时间线」里追加一条**，格式如下：

```markdown
### MM-DD HH:MM · 一句话说清改了什么

**问题**：为什么要改？不改会怎样？（用户反馈 / 自己发现 / 踩坑）
**改动**：具体改了什么。涉及取舍的把取舍写出来。
**结果**：**必须带可验证的数字或现象**，不要只写「已优化」。
**提交**：<commit hash>
```

### 写的时候注意

1. **结果必须可验证。** 「已优化」不算结果，「2MB → 163KB」才算。
2. **踩的坑要单独标出来。** 这类内容对后来的人价值最高。
3. **取舍要写。** 「为什么不用方案 B」比「用了方案 A」更有信息量。
4. **当天就写。** 隔天再回忆会漏掉细节 —— 这份文档的价值全在细节上。
5. **总览表要同步更新**（测试数、表数、配图数这些数字）。

> 如果一次优化跨了好几天（比如等外部账号），
> 就在完成那天记一条，把等待的原因写进「问题」里。
