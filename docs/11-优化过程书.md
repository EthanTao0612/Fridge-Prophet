## 逐日改动

### 09-23 · 立项，打地基

**1. 确定技术栈并锁死版本矩阵** —— Kotlin + Compose + MVVM / FastAPI +
SQLAlchemy 2.0 / 开发 SQLite、生产 Supabase PostgreSQL。

Android 首次构建踩了一堆版本互不兼容的坑（AGP / Kotlin / KSP / Hilt），
最后锁定一套可用组合并写进注释。

**效果**：`assembleDebug` 从「红一片」变成一次通过，并且后来**没有人**
因为「手贱升级依赖」把构建搞挂过。

**2. 立下第一条架构铁律：库存可用性不采信 AI** —— AI 只负责生成菜名和步骤，
「食材有没有、缺多少」**必须由后端拿真实库存重算**。

**效果**：从此不会出现「AI 说你有豆腐，其实冰箱里没有」。
这条规则后来贯穿整个项目，所有涉及可用性的地方都走同一个函数。

**3. 修掉一个真 bug：同一个判断写了两份** —— 菜谱页说「豆腐 ✓ 有」、
采购页却让你去买豆腐。根因是单位换算规则在两处各写了一份。

**效果**：抽出 `_index_stock()` 两处共用，这个矛盾再没出现过。
顺手新增 `scripts/smoke_http.py` —— 补上「进程内测试之外的另一层验证」。

### 09-24 · 从「我能跑」到「别人也能跑」

**1. 做了双击即可运行的 `.bat`** —— 起因是用户反馈「命令行步骤太绕」。

**效果**：Ethan 不用记命令了。代价是踩了两个 Windows 的坑
（`dirname: command not found`、GBK 输出让 awk 静默不匹配）——
**这两个坑后来在部署脚本上又各踩了一次**，所以写进了记忆。

**2. 修 `new-keystore.sh` 传给 keytool 的是 MSYS 路径** ——
Git Bash 的 `/c/Users/...` 原生 Java 认不出来。

**效果**：签名密钥生成从「报错看不懂」变成一条命令。

**3. 真机首次运行，抓到一个启动崩溃** —— 模拟器上一切正常。

**效果**：验证了「模拟器通过 ≠ 真机通过」。**这个教训后来救了好几次**，
也直接催生了「摸不到真机就写契约测试」的做法。

**4. 五条产品反馈落地，其中一条撤掉了 Coil 3** ——
加 Coil 3 之后 Gradle 依赖图序列化异常，编译链直接红。

**效果**：**结论：这个项目的依赖矩阵很脆，能不加依赖就不加。**
后来为「显示密码的小眼睛」宁可写文字按钮也不加图标库，就是这个原则。

**5. 生成菜谱配图，踩到「并行调用互相覆盖文件」** ——
并行 11 个请求只活下来 8 个，3 张的积分白花。

**效果**：**生成图片一律串行。** 后来补 27 张图时严格串行，
一张没浪费。

**6. 用户否掉了程序绘制的插画** —— 原话「你画的是啥东西？？」

**效果**：定下图片标准 **真实照片 + 纯白底 + 单个主体 + 产品摄影质感**，
补齐 40 张真实白底食材图。这个标准后来成了整个图片库的基调。

**7. 文档缺陷两连击** —— ① 文档里给网址加了粗，用户复制时把 `**` 也复制进去了；
② 文档里猜的字段名是错的（`mode` 根本不存在）。

**效果**：**文档里的字段名必须从代码里核出来，不能凭印象写。**

### 09-25 · 推上 GitHub，跑通 CI

**1. 修菜谱页同一道菜重复出现** —— 用户多点几次「生成新菜谱」，
MOCK 模式反复给同样几道菜，库里就攒出十几条同名行。

**效果**：确立「生成式内容落库必须按业务键 upsert」。
**只在前端去重是不够的** —— 删掉一条会顶上来一条。

**2. 口味偏好改成折叠收集箱** —— 一屏塞十几个输入框太挤。

**3. 踩坑：debug 包的后端地址默认是模拟器地址** —— 真机上 App 会
**静默**退回登录页，看起来像账号被清空。

**效果**：`build-debug.bat` 自动检测局域网 IP 并注入。
**这个坑在 10-07 又踩了一次**（release 包指向了一个国内被拦的域名），
症状一模一样 —— 所以「地址必须显式传」这条写进了铁律。

**4. 踩坑：`.bat` 里 `chcp 65001` 和非 ASCII 不能同时出现** ——
chcp 之后 cmd 按**字符偏移**而不是字节偏移继续读文件，
文件里有中文就会静默跳过后续行。

**5. 代码推上 GitHub，CI 首次跑通** —— 调试踩了三个坑：
workflow 文件首次推送不触发构建；`setup-android` 必须 `@v4`；
国内镜像和 GBK 编码在海外 Linux runner 上都有害。

**效果**：每次推送自动出 `app-debug` + `app-release` 两个包。

### 09-29 · 接上真实 AI（项目最重要的一个坎）

**1. 修折叠箱里勾选开关的卡顿与闪烁**

三个坑：① `busy` 是全局的，勾一个开关会让同卡所有开关一起灰掉；
② 等服务器回包界面才动，手感「一卡一卡」；③ 保存后再 `load()` 会多跑请求
且开关先回弹。

**效果**：改成**乐观更新 + 防抖 350ms，失败才 `load` 回滚**。
⚠️ **这个坑在 privacy 修过一次、health 又漏了** —— 所以写进铁律：
加新开关时照抄 `updateHealth`。

**2. 🎉 接上真实 AI（百炼 API Key 配好）** —— 项目从此不再是 MOCK 模式。

实测：

| 操作 | 耗时 | 结果 |
|---|---|---|
| 拍照识别 · 1 样 | 3.4 秒 | 西兰花 0.98 |
| 拍照识别 · 40 样 | 51.5 秒 | 40 种一个不漏 |
| 菜谱生成 · 3 道 | 20.0 秒 | 结构完整 |

**效果**：**关键发现** —— AI 会**自己推出** `category`、`storage_location`、
`shelf_life_days`。所以「食材库要扩到大众冰箱规模」的真实工作量是
**补图片**，不是补名称表。这个判断直接决定了后面几天的方向。

**3. 修检测脚本的假警报** —— `check_ai.py` 用 1×1 的透明 PNG 测视觉模型，
模型直接拒收 —— 这一项**永远不可能通过**，还会给出完全错误的排查建议。

**效果**：**假警报会掩盖真警报。** 后来在图片导入脚本上又遇到一次
（27 张图被误报成「不在规则表里」），同样修掉了。

**4. 上传前压缩图片** —— 客户端把原图直接上传，手机 5000 万像素照片
可能超过 10MB 上限，而报错信息让用户「压缩后再上传」——**App 自己没这功能**。

| | 压缩前 | 压缩后 |
|---|---|---|
| 尺寸 | 4096×3072 | **1200×1600** |
| 体积 | 2.0MB | **163KB** |

**效果**：上传体积**降到 8%**，再没撞过大小上限。

⚠️ 重编码会丢 EXIF 旋转 → **竖拍照片会变横的，AI 看到一台躺倒的冰箱**。
必须手动读 `android.media.ExifInterface` 转正。
⚠️ **四条图片路径必须都覆盖**：头像 / 广场发帖 / 相册选图 / 相机拍照。
相机走 CameraX 直接写文件，**绕过相册那条路** —— 差点只改一半。

**5. 修「菜谱生成来来回回就那几道」** —— 实测连点三次，前两道菜一模一样：

```
第 1 次: 番茄炒蛋、青椒鸡胸肉、西兰花豆腐炒饭
第 2 次: 番茄炒蛋、青椒鸡胸肉、西兰花豆腐炒鸡丁   ← 前两道重复
第 3 次: 番茄炒蛋、青椒鸡胸肉、西兰花豆腐炒蛋
```

**根因**：提示词里完全没提用户已经有什么菜。而落库是按菜名 upsert 的，
重复的名字只覆盖旧行、不新增 —— 所以点多少次列表都长不大。

**效果**：生成时把已有菜名传给模型，明确写「请勿重复」。
修复后同样连点三次 → **9 道零重复**。

**6. 修食材配错图** —— 图片规则对加工食品太宽：

| 食材 | 配成了 | 原因 |
|---|---|---|
| 牛油果 | 牛排 | 被 `beef` 的单字「牛」抢走 |
| 花生米 | 米饭 | 被 `rice` 的单字「米」抢走 |
| 鱿鱼 | 鱼 | 被 `fish` 的「鱼」抢走（海鲜规则白写） |
| 番茄酱 | 新鲜番茄 | 含「番茄」 |
| 花生油 | 一堆花生米 | 含「花生」 |

**效果**：**配错图比没图更糟** —— 用户会以为识别错了，而不是以为缺图。
加了「挡刀区」，把这类规则拦在原料规则前面。这一层后来成了五级降级的第一级。

### 10-04 · 冰箱页分类体系 + 生产数据库接通

**1. 建分类体系（9 个默认分类）** —— 需求是「导入猪肉和牛肉，
它们会被自动分类为肉类」。

分类有三个来源，优先级从高到低：**图片 key > 名字推断 > AI 返回值**。

**效果**：分类和配图永远一致（不会出现「食材在水果组里却配一张蔬菜图」）。
名字推断排在 AI 前面，是因为它**不依赖 AI** —— 手动添加的食材、
MOCK 模式下的食材都能分组，而且同一个名字永远同一类。

**2. 万能图兜底：`具体图 → 分类万能图 → 占位`**

**效果**：图库里没有的「杨桃」会自动退到「水果」的万能图，
而不是显示一个破图。

**3. 自定义折叠箱（后端）** —— 两张新表 + 6 个接口。
用户确认了两个决定：**能同时进多个箱子**（多对多）、**和默认分类并存**。

**效果**：守住两条红线 —— **删箱子不删食材**（只解除归组）、
**不依赖 `ON DELETE CASCADE`**（SQLite 默认不开外键约束，
CASCADE 不生效，会留下孤儿关联行且不报错）。

**4. ⚠️ 踩到一个极难查的坑：204 接口启动时报错**

`Status code 204 must not have a response body` —— 但一模一样的写法
在别的文件里没事。根因是文件顶部的 `from __future__ import annotations`
把 `-> None` 变成字符串，FastAPI 解析出 `NoneType` 类型对象，
而 `bool(NoneType)` 是 True。

**效果**：**报错位置和真正原因完全不在一处。** 这条教训后来在
「`_universal-other` 被当成兜底」时又验证了一次。

**5. 🎉 生产数据库接通（Supabase）**

| 项 | 结果 |
|---|---|
| 数据库连接 | ✅ 连接池 2.3 秒通，**20 张表自动建好** |
| 图片 bucket | ✅ `fridge-photos`（公开）已创建并双向验证 |
| `.env` | ✅ 三个值全部配好 |

**过程中挖出三个坑：**

**① Supabase 新版令牌默认「No access」** —— 第一次给的令牌只有身份验证、
读不了任何东西（403）。必须手动勾 `Project → Read` 和 `Application services → Read`。

**② 本机网络按 SNI 拦截 `*.supabase.co`** —— 诊断过程：

```
同一个 Cloudflare IP，只换 SNI：
  SNI = <项目>.supabase.co   ✗ 连接被重置
  SNI = api.supabase.com      ✓ TLSv1.3
  SNI = www.cloudflare.com    ✓ TLSv1.3
  www.google.com              ✗ 超时（说明是 GFW 级别，不是本机代理）
```

**效果**：影响很小 —— 数据库走 PostgreSQL 协议不受影响；
只有 Storage 上传在本地失败，按设计退回本地磁盘。
**部署到香港服务器后这个问题不存在了**（10-07 实测 Storage 直连正常）。

**③ 创建 bucket 的两条绕行路** —— 管理 API 只有读 bucket 的接口、没有创建的。
于是**直接往 `storage.buckets` 表插一行**（bucket 元数据就存这儿，
和 Storage API 内部做的事一样），再用管理 API 独立确认。

**6. 一个提醒：配好之后本地 `.env` 就指向生产库了** ——
**不能跑 `tests/test_e2e.py`**，它会注册几十个测试账号进去。

**效果**：后来改成测试在导入 app 之前就把 `DATABASE_URL` 指向临时 SQLite，
随时可以跑（见 10-06）。

### 10-06 · 一天之内，项目从「能演示」变成「能交付」

这一天是整个项目改动最密集的一天。**15 项改动**，覆盖内容资产、
性能、安全、客户端四条线。

#### 一、内容资产：把「图不够、菜不够、知识不够」三件事一起解决

#### 二、性能：冰箱页 850ms → 169ms

Ethan 反馈「体验下来感觉很卡很慢」。

**8. 定位根因：生产库在孟买，单次往返 169ms**

`SELECT 1` 和查真实表都是 169ms → **纯网络延迟，不是查询慢**。
而冰箱页要发 3 个请求，其中**两次是白花的**。

**9. 读接口不再无条件写库（省 169ms）**

`list_inventory` / `list_expiring` / `inventory_stats` 每次**读**都要
`db.commit()` 一次 —— 只为持久化「新鲜度」这个派生字段。
而 commit 是一次**完整的网络往返**。绝大多数请求里新鲜度根本没变。

**效果**：改成「有变化才 commit」。

⚠️ 不能用 `any(...)` 收集结果 —— 它会在第一个 True 处短路，
后面的食材就不会被刷新了。必须老老实实跑完整个循环。

**10. 折叠箱列表合并成一次查询（省 169ms）** ——
原来「查箱子 + 查成员」两次往返 → 合成一次 LEFT JOIN。

⚠️ 用 **outerjoin 不用 join** —— 空箱子也要返回。
用户刚建完还没放东西，inner join 会让它凭空消失。

**11. 客户端三个请求改成并发（省 680ms）** ——
`async {}` 三个一起发；**先 await 食材列表**（用户真正在等的）。

| | 之前 | 现在 |
|---|---|---|
| `/inventory` | 342ms | **169ms** |
| `/food-categories` | 338ms | **169ms** |
| 客户端总耗时 | 串行 849ms | **并发 169ms** |

**效果：约 5 倍。** 这是全项目单次收益最大的一次优化。

⚠️ **通用教训：远程数据库的「读」不要顺手写。**
每次 commit 都是一次网络往返，在本地 SQLite 上完全感觉不到。
**判断标准**：这个写操作是「业务需要」还是「顺手持久化派生字段」？

**12. ⚠️⚠️ 又一个性能坑：74 秒 → 12 毫秒**

改完之后「菜谱列表」慢到 **74 秒**。两个叠加的问题：

**① `commit()` 让对象过期 → N+1 懒加载**

`_load_inventory` 里有个 `db.commit()`，而 SQLAlchemy 的 commit
**默认会让 session 里所有已加载对象过期**，之后每访问一个字段
都会触发一次 SELECT。列表是先查菜谱、再取库存，于是 200 道菜
每个字段一次查询 —— **200 × 169ms = 34 秒**。

修法两条：`_load_inventory` **没变化就不 commit**；
调用方**先取库存、再查菜谱**，让 commit 发生在菜谱被加载之前。

**② 数据量本身**：192 道完整菜谱是 **482KB**，从孟买拉回来 4 秒。

**效果**：`materialize` 从 8.7 秒（AI）降到 **约 960ms**。
另外把 `visible_user_ids` 加了 per-session 缓存（它在同一个请求里
会被调好几次，每次 169ms）。

**13. 加了 GZip 中间件**

**效果**：JSON 压缩 70-85%，实测 **19602 → 7265 字节（省 63%）**。
`minimum_size=1000` 是故意的 —— 小响应压缩后反而更大。

#### 三、安全：把「免费刷额度」的口子堵上

**14. 注册加邮箱验证码（Ethan 发现的安全洞）**

Ethan 提出：「我不确定是不是现在邮箱随便输入一个什么东西都能注册成功，
我要那种真实意义上的绑定，类似于需要发验证码的那种。」

**他判断得对。** 实测：

```
a@b.com                    → 201 注册成功 ✗
test@nowhere-xyz-12345.com → 201 注册成功 ✗
不是邮箱                    → 422（EmailStr 拦住了格式）
```

`EmailStr` 只校验**格式**，不验证邮箱是否真实存在 —— 邮箱那一栏形同虚设。

**效果**：SMTP 发信（标准库 `smtplib`，**不引入新依赖**），
新增 `email_verifications` 表 + `POST /auth/send-code`。
**四道闸**：同邮箱冷却 60 秒 / 同邮箱每日 10 次 / 验证码 5 分钟有效 /
最多尝试 5 次。**端到端 276 → 286 项。**

⚠️ **不做账号枚举**：邮箱已注册时也返回成功（只是不发码），
响应结构和正常情况**完全一致**。否则攻击者能拿这个公开接口
批量探测「某个邮箱在不在这个平台上」。

⚠️ **验证码存 sha256 不存明文**，加邮箱当盐。故意**不用 bcrypt** ——
6 位码本身防不住离线破解，真正的防线是「5 次上限 + 5 分钟过期」，
用 sha256 是为了校验快（bcrypt 单次 100ms）。

⚠️ **注册失败返回 400 而不是 401** —— 401 会触发客户端的
「登录失效」处理，把用户直接踢回登录页。

**15. 真机反馈后修的三个问题**

**① 验证码明明是对的却提示「不正确」** —— 查日志发现他**发了两次码**，
然后用了先发的那一个，而原设计是「发新码就作废旧码」。

**效果**：改成**不再作废旧码**。安全性没有实质下降 ——
每个码都有 5 分钟有效期和 5 次尝试上限，加上每天 10 次发码上限，
暴力破解窗口最多 50 次尝试，而 6 位码有 100 万种可能。
**宁可让「用户用旧码」也能成功，也不要让他对着一个正确的码反复被拒。**

**② 密码框里有一串自己没打过的圆点** —— 是 **Android 密码管理器自动填充**的。

**效果**：注册模式下给密码框加 `ContentType.NewPassword` 语义，
告诉系统「这是**新**密码，别填旧的」。

**③ 密码框需要「小眼睛」** —— **用文字按钮而不是图标**，
项目里没引 `material-icons-extended`，为一个眼睛加依赖不值得。

**16. 邮箱服务接通（163）** —— QQ 邮箱卡了几轮之后换成 **163，一次就通**。

**效果**：发信耗时 1.6 秒，启动日志 `邮箱验证码: 已配置（smtp.163.com）`。

**QQ 为什么不通**（记下来，以后少踩）：
① QQ 的授权码是「每次点生成，上一个立刻作废」，用户拿到手里的很可能是废码；
② QQ 对连续重试很敏感，报错在 `502` 和 `535` 之间轮换，
**根本分不清是授权码错还是被限流**。
③ 调试时**原始 SMTP 对话**比 `smtplib.login()` 的报错清楚得多。

> **教训：SMTP 认证失败不能像调 API 那样连着重试。**
> **推荐顺序**：163 / 126 > QQ。

**17. 给百炼额度上一道保险（AI 每日配额）**

**起因**：后端的接口**原本没有任何限流**，而注册是开放的 ——
理论上任何人发现域名后注册个账号，就能反复调 `/vision/scan`，
**每一次都在花项目自己的钱**（识别一张图约 2 分钱）。
对学生参赛项目来说，「被人刷掉几十块」不是理论风险。

**两道闸，缺一不可：**

| 层 | 作用 | 默认 |
|---|---|---|
| **按用户** | 防单个账号霸占额度 | 30 次/天 |
| **全站** | **给账单兜底** | 500 次/天 |

**只有按用户限流是不够的** —— 攻击者注册 100 个账号就拿到 100 倍额度。
全站那条才是真正的「最多花多少钱」。

**效果**：生产库实测 —— `/vision/status` 返回 `ai_quota_left: 30` →
调一次 → 变成 `29`，`ai_usage` 表里 `user=1` 和「全站」各 1 条 ✓。

⚠️ **配额落库不放内存** —— 放内存的话每个 worker 各算各的
（实际额度 = 配置 × worker 数），重启还会清零。
代价是每次 AI 调用多约 700ms，但 AI 本身要 2.6~20 秒，可以忽略；
而**配额不准就等于没有配额**。

⚠️ **`materialize` 只在 AI 兜底分支扣** —— 正常情况它是查库返回（不花钱）。
放在函数开头会让每次点推荐菜都白扣一次。

⚠️ **`user_id = -1` 表示全站** —— 用 NULL 更自然，但 `(user_id, day)`
的唯一约束在 **PostgreSQL 里对 NULL 失效**，能插出无数行。

⚠️ **已知的并发缺口，故意不修**：「先读再写」不是原子的，
两个并发请求可能都读到 `count = 29`，实际变成 31 次。
要修就得加行锁，那会让每次 AI 调用再多一次往返。
对一个「防滥用」而不是「精确计费」的场景，多放行一两次完全可接受。

**18. 扫描页显示「今日还剩 N 次 AI 识别」**

后端加了配额，但**客户端一个字都没显示** —— 用户被 429 拦下来时
才第一次知道有「额度」这回事，感受就是「昨天还好好的，怎么突然不行了」。

**效果**：拍照前就能看到还剩几次，快用完（≤3）提示「省着用」，
**用完则把拍照和相册都禁用**，并说明「仍然可以手动添加食材」。

⚠️ **一个容易写错的细节：默认值必须是 -1 而不是 0** ——
`-1` 表示「**还不知道**」（状态接口失败）。写成 `0` 的话，
**状态接口一失败就会把拍照按钮灰掉**，把网络问题显示成了额度问题。

⚠️ **这次没有在真机上验证** —— 手机锁屏了而且需要 PIN，
**我没有去绕**（那是别人的手机）。改用 **MockWebServer 契约测试**
（`AiStatusContractTest`，5 个用例）。它抓的正是这次的真实风险 ——
**不是崩溃，而是字段名对不上**：客户端配了 `ignoreUnknownKeys`，
后端加字段不会解析失败；但客户端漏了 `@SerialName` 的话，
解析出来就是默认值，**不报错但功能静默失效**。

#### 四、客户端：把「做了一半」的功能全部收口

**19. 冰箱页按分类折叠** —— Ethan 最早提的那个需求，后端早就做完了，
客户端一直没动。

**效果**：真机效果 —— 按分类分组、顺序由后端给（蔬菜在前、「其他」垫底）、
配图全对。新增 `GET /inventory/categories` 返回顺序和数量。

**为什么客户端要单独问一次**：顺序只在 `CATEGORIES` 里定义一次。
客户端抄一份迟早不一致 —— 改了后端忘了改客户端，分组顺序就会很怪。
同「可见范围只能有一处定义」原则。

⚠️ **踩了三个 Compose 的坑**：`LazyListScope` 的扩展函数不能标 `@Composable`；
辅助 composable 必须是顶层函数；替换代码块时容易吃掉函数的闭合括号
（改完先用**括号深度检查**，别等编译器报）。

**20. 折叠箱终于能管了（真机 5 条链路全部验收）**

折叠箱这个功能之前**只做了一半**：后端 6 个接口齐全、ViewModel 的方法
也写好了，但**界面上一行都没接**。结果是：能看折叠箱，但**建不了**；
就算建了也**没有任何入口能把食材放进去**。

**效果**：一个建不出、也装不进东西的箱子，等于没有 —— 现在补齐了。
真机 5 条链路（新建 / 加食材 / 重命名 / 移出 / 删除）**后端日志全部对得上**。

**「删除箱子不删食材」单独验证过** —— 删完箱子后，菠菜和红椒仍然在
「按分类 → 蔬菜」里，只是不再归属那个箱子。
这是这个功能最容易被误解的地方 —— 用户在确认框里看到「不会被删掉」
才敢点。

**21. 顺手修掉的两个问题**

**① 冰箱为空时，整个列表不渲染 → 折叠箱入口消失** ——
条件是 `state.items.isEmpty() -> EmptyState(...)`，但折叠箱的管理入口在
**那个 LazyColumn 里面**。改成 `items.isEmpty() && boxes.isEmpty()`。

**② 折叠箱里的食材行被折成 5 行** —— `IconButton` 是 **48dp 最小尺寸**，
一行三个动作 = 144dp，食材名那一列只剩不到 40dp。

**效果**：换成自绘的紧凑点击区，三个动作合计约 92dp，**省下 50dp**。

**22. 接着补上排序（同一类「做了一半」）** ——
`sort_order` 后端一直支持，但客户端完全没用。

**效果**：后端加了一个新接口 `PUT /food-categories/order`（整批传完整顺序），
而不是复用单条 `PATCH` 挪一格：

| | 单条 PATCH 挪一格 | 整批 PUT（选了它） |
|---|---|---|
| 服务端要知道当前顺序 | **要**（得先读一次） | 不用 |
| 两次操作之间 | 有窗口，两设备同时挪会互相覆盖 | **幂等**，后到的赢 |
| 请求数 | 2 次 | **1 次** |

**23. 菜品库接入 App（192 道家常菜终于用上了）**

**效果**：菜谱页「推荐」标签（默认选中）—— 「根据你冰箱里的食材，
有 9 道现在就能做」。实测（13 样食材的冰箱）：100 道候选，
**19 道食材齐全，100/100 都有专属配图**。

① `ingredient_image_service` 和 `food_image_service` **各有一个 `_exists`**，
我 import 错了，结果**每道菜都显示「没有配图」而且不报错** ——
图片静默消失，只能靠肉眼看出来。
② 替换代码块吃掉闭合括号 —— **第二次了**。
**判断标准：连续两次修改都没解决同一个问题时，立刻 `git checkout` 恢复重来。**
在错的基础上继续补只会越补越乱。

**24. 推荐菜真的能点进去了（真机验收通过）**

**效果**：点一张卡 → 卡片原地变成「AI 正在写做法，约需 10~20 秒」
（配图位置换成转圈，卡片不跳高），其余卡片压暗到 55% →

#### 五、架构：把菜谱的「读」和「写」彻底分开

**25. 菜品库 192 道菜的做法全部预写进数据库（点开不再调 AI）**

Ethan 的原话：

> 「我不要这种每次点开都 ai 现场生成的，我要那种本来就现成的，
>   根据食材生成出来的菜谱是数据库里有的，
>   扩充了这么多的菜品都要在数据库里写好热量做法等等」

之前 `materialize` 是「点开才让 AI 现写」，第一次点要等 **8.7 秒**。

**效果**：离线生成一次（`tools/generate-dish-recipes.py`，33.7 分钟 /
190 次 AI 调用）→ 存进数据库 → 点开是查库返回。
**用 `user_id = NULL` 表示「系统内置」** —— 一份记录所有用户共用，
包括评委新注册的账号，不用为每个用户各存一份，也不用调 AI。

⚠️ **读和写的可见范围必须分开**，这是这次最容易出事故的地方：

| | 范围 | 用在哪 |
|---|---|---|
| `readable_recipe_clause` | 系统内置 + 自己/家人 | 列表、详情、做菜预览、扣库存、采购清单、广场分享 |
| `editable_recipe_clause` | 自己/家人（**不含内置**） | 按菜名查重、删除 |

**不分开的后果**：用户能**删掉系统内置菜谱** —— 那是所有用户共用的一条记录，
删一次全都没了。所以删除走 `editable`，而且内置的给 **403 而不是 404**
（用户明明看得见详情页，说「不存在」是自相矛盾的）。

⚠️ **又一个只在 Postgres 上才炸的坑**：灌库时报
`StringDataRightTruncation`。模型偶尔在 `unit` 字段里塞注释
（`汤匙（即oyster-sauce）` 17 个字），而 `VARCHAR(16)` 在 **SQLite 上
不校验长度**，所以本地测试全过、只有生产库会炸。

**效果**：`clean_unit()` 在写库的两个入口共用，
去括号注释 → 去残缺分数的前导斜杠 → 还是超长就退成 `份`
（**兜底而不是截断** —— 截断只会得到「汤匙（即oyster-sa」这种更莫名其妙的值）。

**26. 生成菜谱改成查库（不调 AI）**

Ethan 的判断：「生成菜谱我觉得不需要调用 ai，做一个类似于关键词提取器的内容，
因为数据库里有的菜品都会写需要什么食材。」

**完全正确。** 菜品库里每道菜都标了必需食材，这件事**查表就能算**。

| | 改前 | 改后 |
|---|---|---|
| 耗时 | 约 20 秒 | **毫秒级** |
| 成本 | 每次调 AI | **0** |
| 扣配额 | 扣 1 次 | **不扣** |
| 结果 | 每次可能不同 | 同冰箱同结果 |

**效果**：AI 从此**只用在拍照识别上** —— 那才是真正需要视觉理解的地方。

**27. 采购项变暗响应慢 → 改成乐观更新**

**根因**：点「买好了，写回冰箱」之后是「等服务器逐条写库存 →
再拉一次全量 → 卡片才变暗」。而写回是**逐条**改库存（每条还要跨家庭查同名合并），
生产库 169ms/次，10 项就是一两秒。

**效果**：点下去**立刻变暗**，再用服务端返回的数据替换本地
（顺带省掉一次多余的 `load()`）。

⚠️ 「整单完成」的判定规则要和后端一致，否则会出现
「界面变暗了但服务器还是 pending」，下次刷新又弹回来。

**28. 静态图片没有 `Cache-Control`（这条影响最大）**

从后端日志里数出来的：打开冰箱页触发 **35 个食材图请求**、
菜谱页推荐列表再触发 **40 多个菜谱图请求**，**全是 304**。

**根因**：FastAPI 的 `StaticFiles` 只发 `etag` / `last-modified`，
**不发 `Cache-Control`** —— 客户端**每次都要回来问一遍**「这个还能用吗」。

**效果**：加 `Cache-Control: public, max-age=86400` 后，
客户端直接用本地副本。真机实测：**第一次启动 80 个图片请求（全 304），
第二次启动 0 个**。**这条是纯白捡的性能。**

#### 六、工程化：把部署从「1-2 小时手工」变成「一条命令」

**29. 新增 `tools/deploy.sh`**

`docs/03` 里那套手工步骤有 6 大步、十几条命令，中间要改 3 个配置文件，
每一处都能写错（缩进、路径、端口、`server_name`），报错还都很晦涩。

**效果**：一条命令做完 —— 装依赖 → 建 `fridge` 用户 → 拉代码 →
建虚拟环境 → 生成 `.env` → 跑测试 → 配 systemd → 配 Nginx → 上 HTTPS →
配 Supabase 保活 cron → 自检。

**几个刻意的设计：**

| 决定 | 为什么 |
|---|---|
| **可重入** | 中途失败修好后**再跑一次**就行，做过的步骤跳过 |
| **不用 root 跑服务** | systemd 里 `User=fridge`。root 跑的话服务被攻破 = 整台机器失守 |
| **uvicorn 只监听 127.0.0.1** | 外部流量一律走 Nginx。监听 `0.0.0.0` 会绕过 HTTPS |
| **`.env` 权限 600** | 里面有密钥，只给 `fridge` 读 |
| **密钥现生成** | 不沿用开发环境那份 `SECRET_KEY` |
| **certbot 失败不中断** | 证书签不下来通常是 A 记录还没生效，这时候 HTTP 仍然能用 |
| **结尾自检** | 把「连的是 Supabase 还是 SQLite」「图片存哪」直接打出来 |

⚠️ **没法端到端验证，所以把纯逻辑抽出来自测** ——
本地没有 Docker，WSL 被安全策略挡住，**装包 / systemd / Nginx / certbot
那几步我一次都没跑过**。这一点必须说清楚，不能假装验证过了。
能做的是把**最容易静默出错**的纯逻辑抽成函数，配 `--selftest` 模式
（12 项，不需要 root）。**写自测时立刻抓到一处逻辑错**：
我原来给**任何**非空连接串都补 `sslmode`，包括 `sqlite:///x.db` ——
sqlite 不认这个参数，启动时才报错。

> **结论：没法端到端验证的脚本，至少把纯逻辑抽出来自测，
> 并在文档里明说哪部分没验证。** 这比「看起来很完整」诚实，也更安全。

（怕抢走玉米罐头）。理由没错，但漏了 —— **不写兜底 = 光秃秃的「罐头」没有图**。

**效果**：补兜底 + 补例外（顺序是关键：规则按顺序 + 子串匹配，

**2. ⚠️ 排查中发现的真问题：端口 8000 上有两个后端在跑**

改完代码后接口还是返回香菇红枣，但直接 import 模块算出来是对的 ——
**说明跑着的进程用的不是新代码**。`netstat` 显示 8000 端口有**两个**
LISTENING，而旧进程在 netstat 里的 PID **根本不存在**
（监听套接字被子进程继承了，按 PID 杀杀不到）。

**效果**：这条教训在**部署时又用了一次**（见下面第 9 条）。

**3. ⚠️⚠️ 部署前预演：数据库连接数会不够（会让部署直接崩）**

服务器还没到手，先把 `deploy.sh` 过一遍。翻到连接池配置时顺手实测 ——
**Supabase 的连接池只允许 10 条并发连接**，第 11 条直接报
`(EMAXCONNSESSION) max clients reached`。

而原来的配置是 `5 + 5 = 10` **每个 worker**，注释里还写着
「两个 worker 一共 20 条，留出余量」—— **20 > 10，一个 worker 就吃满了**。

**效果**：改成每个 worker 4 条 + worker 封顶 2 个（4×2=8 ≤ 10），
并在 `deploy.sh` 里**加了一步主动试连的自检**。
后来部署时这一步输出 `✓ 连接预算够用（开满 8 条连接）` ——
**它真的挡住了这个坑。**

⚠️ **这个错只在并发高的时候才冒出来** —— 也就是**演示当天有人一起用的时候**，
而且报错是「连不上数据库」，完全看不出是连接数的问题。

**4. 清掉所有「还在说 AI 生成菜谱」的文案**

改了实现之后，界面上和文档里有一批地方**还在说 AI** ——

**效果**：界面改 5 处、README 改 4 处，另外把过时的「251 项测试」

而不是「缩水」：「AI 离线生成内容 + 运行时规则匹配」既保留了 AI 的内容质量，
又拿到毫秒级和可复现的结果 —— **答辩时这是加分点，不是减分点。**

#### 二、上线：一条命令，和一个被 DPI 拦住的域名

**5. ⚠️⚠️ 部署完 App 登录报「网络异常」—— 根因是 `nip.io` 在国内被拦**

`deploy.sh` 原来推荐「没域名就用 `1.2.3.4.nip.io`」。**这个建议是错的。**

实测（手机 · 中国移动数据）：

| 测试 | 结果 |
|---|---|
| 直接连 IP `http://119.28.182.46/health` × 3 | **404 404 404**（每次都到服务器 ✓）|
| 用 `119.28.182.46.nip.io` × 3 | **000 000 000**（每次都被拦 ✗）|
| 百度 | 200 ✓ |
| **api.github.com**（海外站对照）| **200** ✓ |

**不是运营商或网络的问题**（GitHub 都通），是 **`nip.io` 这个域名本身
在国内被按 Host 头 / SNI 做了 DPI 拦截** —— 连「连 IP 但带 nip.io 的
Host 头」都会被拦，说明拦的是**名字**不是 IP。

**效果**：改掉所有「没域名用 nip.io」的建议，并在 `docs/03` 顶部加了

服务器本机、浏览器代理、境外网络全都正常。

**6. Nginx 读不到 static/ → App 里一张图都不显示**

`/static/` 下所有文件返回 **403**，而 `/health` 和 11 个接口全部正常。

**根因**：`adduser` 建的 `/home/fridge` 是 `drwxr-x---`，
而 Nginx 的 worker 以 **www-data** 跑，**穿不过这个目录**。
Nginx 错误日志：`open() ".../tomato.jpg" failed (13: Permission denied)`。

**效果**：`usermod -aG fridge www-data` + `systemctl restart nginx`
（要用 restart 不是 reload —— 附加组要重新拉进程才生效）。
修完 4 张图全部 200，而且 `.env` 仍是 600、**www-data 读不到** ✓。
已写进 `deploy.sh`，并在自检里**单独加了一条查 `/static/` 的图** ——
静态图不走 Python，「接口全通」根本不代表图能显示。

**7. ⚠️ 部署脚本在 Linux 上跑不起来 —— Windows 的 CRLF 换行**

用 scp 把 `deploy.sh` 传到服务器后直接执行：

```
line 50: set: pipefail: invalid option name
退出码: 2
```

**报错完全看不出是换行符的问题** —— 看起来像脚本语法错。

**效果**：加了 `.gitattributes` 强制 `.sh/.py/.md/.yml` 用 LF，
以后不会再踩。

**8. 修好「部署完必跑一次」的冒烟脚本，并在服务器上跑通 62 项**

`scripts/smoke_http.py` **已经跑不通了** —— 注册接口后来加了邮箱验证码必填，
而验证码**只会发给真实邮箱**（库里存哈希、配了 SMTP 后不再打日志、

**效果**：脚本**自己按同样的算法造一个码、直接插一条记录** ——

**按天记录，一天一节，不按时间段分。** 一天里做了几件事，
就在那一天下面**编号**列出来。

```markdown
### MM-DD · 一句话说清这天的主线

**1. 这次改动的标题** —— 为什么要改（用户反馈 / 自己发现 / 踩坑）。

**效果**：**必须带可验证的数字或现象。**「已优化」不算结果，
「850ms → 169ms」才算。

**2. 下一个改动** —— ……
```

### 写的时候注意

1. **按天，不按小时。** 一天里上午下午连着做的算同一天，合并成一节。
2. **一次改动一个编号。** 别把三件事塞进一段散文里。
3. **效果必须可验证。** 数字、现象、或者「真机验收通过」。
4. **踩的坑要单独标出来（⚠️）。** 这类内容对后来的人价值最高。
5. **取舍要写。** 「为什么不用方案 B」比「用了方案 A」更有信息量。
6. **当天就写。** 隔天再回忆会漏掉细节 —— 这份文档的价值全在细节上。
7. **总览表要同步更新**（测试数、提交数、配图数这些数字）。

> 如果一次优化跨了好几天（比如等外部账号），
> 就在**完成那天**记一条，把等待的原因写进「为什么」里。
