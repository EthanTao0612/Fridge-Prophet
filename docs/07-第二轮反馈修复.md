# 07 · 第二轮反馈修复

小组在真机上试用之后给了 5 条反馈。这一份逐条记录「原来的问题 → 现在的做法 → 代码在哪」。

和 `06-本轮优化说明.md` 是同一个格式，只是换了新一轮反馈。

## 反馈 ①：家庭成员要能关联真实账户

> 原话：「优化为可关联其他账户的形式，可邀请其他人一同管理冰箱，并且可以选择被邀请人以什么身份加入自己的冰箱或家庭，在同一个家庭的人可以共享冰箱中的数据或者菜谱等」

### 和原来那个「家庭成员」的区别（重要，别搞混）

项目里现在有**两套**「家人」的概念，并存、各管一摊：

| | `FamilyMember` | `Family` + `FamilyMembership` |
|---|---|---|
| 是什么 | **忌口档案**（「爷爷不吃辣」） | **账号关联**（妈妈有自己的 App 账号） |
| 对方要注册吗 | 不用 | 要 |
| 共享什么 | 什么都不共享 | 冰箱、菜谱、采购清单 |
| 用来干什么 | 生成菜谱时避开全家忌口 | 一起管理冰箱 |
| 接口 | `/users/family` | `/family` |

**为什么不合二为一**：合并会让「没有账号的家人」无处安放。
爷爷奶奶大概率不会装这个 App，但他们的忌口必须被考虑进去。

> 顺带把个人页那张卡从「家庭成员」改名成了**「家人的忌口」** ——
> 新加了「我的家庭」之后，两张卡都叫「家庭」会让人以为重复了。

### 邀请码自带身份

需求里那句「**可以选择被邀请人以什么身份加入**」，落在 `Family.invite_role` 这一列：
家庭主生成邀请码时就把身份定好，而不是等人进来了再补。

可分配的身份只有两种，**故意不含「家庭主」**：

- `member` 成员 —— 能看能改
- `viewer` 只读 —— 能看不能改

为什么不做转让家庭主：那要处理原主人降级、避免出现两个主人或没有主人，
是一整套状态机。想换主人的话，解散重建更简单，也不会留下半吊子状态。

### 一个用户只能在一个家庭里

`FamilyMembership.user_id` 上有唯一约束。

允许多家庭会让「冰箱页显示的到底是哪个家的」变成一个需要解释的问题，
而用户心里其实只有一个「我家」。要换家庭就先退出。

### 数据共享：一个函数定生死

新增 `family_service.visible_user_ids(db, user_id)` —— **全项目唯一**定义
「谁的数据算我的」。没加入家庭时返回 `[user_id]`，所以调用方不用写
「先判断有没有家庭」那一套 —— 少一个分支就少一处能写错的地方。

冰箱 / 菜谱 / 采购的**读**查询全部改走它。写操作仍然记在添加者名下。

**为什么必须收敛到一处**：漏改一处就会出现「冰箱里看得到、菜谱里看不到」这种自相矛盾。
和铁律 6（判断「食材有没有」只能有一处实现）是同一个道理。

几个容易漏的地方，都处理了：

- **同名合并也要跨家庭**。扫描入库、采购写回时找「冰箱里已有的同名食材」，
  范围必须是全家 —— 共享冰箱是同一个物理空间，家人买过牛奶、我再买一盒，
  应该是「多了一盒」，而不是冰箱里出现两行牛奶。
- **菜谱查重跨账号**。妈妈生成过「番茄鸡蛋豆腐」，我再生成一次，
  列表里不该出现两张一样的卡片（这是第一轮修过的 bug 的跨账号版本）。
- **「清空冰箱」清的是看得见的全部**，包括家人加的。按钮写着「清空冰箱」，
  如果点完还剩家人的食材，用户会以为功能坏了 —— 范围必须和列表里看到的完全一致。

### 权限

| 操作 | owner | member | viewer |
|---|---|---|---|
| 看冰箱 / 菜谱 / 采购 | ✓ | ✓ | ✓ |
| 改冰箱 / 菜谱 / 采购 | ✓ | ✓ | ✗ 403 |
| 记录自己的口味反馈 | ✓ | ✓ | ✓ |
| 换邀请码 / 调成员身份 / 移出成员 | ✓ | ✗ | ✗ |

两条特殊规则：

- **家庭主退出 = 解散整个家庭**。不能一走了之 —— 那会留下一个没有管理员的家庭，
  剩下的人既改不了设置也没法邀请人。确认框里把这件事写清楚了。
- **移出成员只解除关联**，对方自己加的食材和菜谱都留着。被移出不等于东西被没收。

个人数据（饮食画像、健康偏好、身体数据）**不共享**，这条从第一轮起就没变。

## 反馈 ②：各个功能块的界限不是特别明显

### 根因是配色，不是布局

翻了一遍发现：浅色主题下**背景 `#FFFDFB`、卡片 `#FFFFFF`，色阶只差 0~4** ——
等于白底上放白卡，卡片边界根本看不见。而 `SectionCard` 又是零阴影、无边框。

深色主题只差 9，也偏糊。

### 改法

| | 改前 | 改后 |
|---|---|---|
| 浅色背景 | `#FFFDFB` | `#F4F2EC`（暖调浅灰） |
| 浅色嵌块 | `#EFEDE9` | `#E9E6DF` |
| 深色背景 | `#12140F` | `#0E100C` |
| 卡片 | 无边框 | 1dp `outlineVariant` 发丝边框 |

浅色背景和纯白卡片现在差 11~19 个色阶，和 iOS 分组列表同一档。

**加边框的原因**：白色卡片叠在浅灰背景上、又没有阴影时，光靠色差边界会发虚。

### 差点引入的回归

`surfaceVariant`（`#EFEDE9`）原本是给「卡片内嵌块」用的。
背景改成 `#F4F2EC` 之后，这两个色几乎一样了 ——
**引导页那根用 `surfaceVariant` 当「未完成」色的进度条会看着缺几段**。

教训：**改主题色必须把所有引用该颜色的地方过一遍**，
不能只盯着「卡片对背景」这一组关系。

### 覆盖面

`SectionCard` 用在 11 个页面 42 处；加上主题色是全局生效。
菜谱卡片和广场卡片各自写了 `Card`，也统一加了边框 ——
否则两种卡片混排时边界观感不一致。

## 反馈 ③：折叠箱编辑一下就自己收回去

> 原话：「打开健康偏好或者饮食偏好和隐私设置这些折叠箱的时候，现在的状态是我编辑一下他就自己收回去了，能不能设置为我把他拉开后，手动把他关上」

### 根因

`CollapsibleCard` 用 `rememberSaveable` 记展开状态，但个人页 `LazyColumn` 里的
item **没有指定 key**。Compose 在没有 key 时用「位置」当身份。

而那张「保存成功」提示条是**条件渲染**的：用户一编辑它就插进列表，
后面所有 item 的位置全部往后挪一位 —— Compose 就认不出「还是原来那个折叠卡」了，
`rememberSaveable` 里的展开状态随之被重置。

### 修法

给个人页 `LazyColumn` 的**每一个 item 都加上稳定 key**（`profile-header`、
`preference`、`health`、`family`、`privacy` 等 10 处）。

加上 key 之后，item 的身份和位置解耦，提示条插进来也不会影响别人。

## 反馈 ④：食材支持按重量 + 手动填保质期天数

> 原话：「在统计食材的时候，除了可以选择多少个食材，还支持选择质量，手动添加食材的时候支持自己输入保质期的天数」

- **单位加快捷项**：个 / 克 / 千克 / 毫升 / 升 / 斤 / 盒 / 袋 / 把 / 颗。
  保留自由输入是为了「半把」「1 提」这种没法枚举的量；
  但高频单位点一下比手打快，也不容易打成「kg」「G」这种后端认不出的写法 ——
  单位对不上会被当成「大概率有」，采购清单就会漏东西。
- **保质期加「或自己填天数」输入框**，和上面的快捷项互斥：
  填了就以手填的为准，快捷项自动取消高亮。
  包装上印「保质期 45 天」这种不在预设里的值，现在能填了。

## 反馈 ⑤：做菜之后自动更新冰箱库存

> 原话：「加入一个自动更新冰箱库存的功能，比如在我浏览了某一道菜之后，我可以选择是否做这道菜，若选择，会给出大概需要多少食材，并根据系统的估算更新冰箱的库存，同时用户可以选择是否按照系统的估算进行删减库存，可以自由的输入数量或者质量，并实时的更新库存，也可以选择取消不进行更改等」

### 接口

| 接口 | 作用 |
|---|---|
| `GET /recipes/{id}/cook-plan` | 只算不扣的预览 |
| `POST /recipes/{id}/cook` | 按实际用量扣减 |

**为什么要有预览**：扣库存不可逆 —— 扣完那行食材就没了。
不能点一下按钮就闷头扣，得先让用户看见「会用掉什么、各多少」，能改数字，再确认。
取消就什么都不动。

### 三个关键设计决定

**1. 扣减规则和缺料判断共用同一套食材匹配**

把库存索引抽成 `recipe_service._index_stock()`，`recompute_availability`
和新的 `build_cook_plan` 都用它。

理由：食材匹配要是两处实现，就会出现「菜谱说食材齐全，一点『做这道菜』
却告诉你冰箱里找不到」。这正是铁律 6 记的那个坑。

**2. 单位对不上时不猜**

库存记「1 盒豆腐」、菜谱要「300 g」，两者没法换算。这时候：

- 给个「大概扣 300」是错的 —— 可能把整盒扣没
- 给 0 也是错的 —— 用户以为扣了，其实什么都没发生

所以 `suggested_deduct` 返回 `None`，前端渲染成空输入框让用户自己填。
和缺料判断「单位无法换算时按大概率有处理」是同一个态度：**不装懂**。

**3. 扣到 0 就删行**

库存表达的是「现在还有什么」。留一条数量为 0 的记录只是冰箱页的噪声。

### 客户端

- 详情页加「我做这道菜了」主按钮 → 弹确认窗
- 弹窗列出每项：食材名、冰箱余量、可编辑的扣减量
- 单位对不上的项留空 + 标红提示，说明为什么不能自动算
- 一个「同时更新冰箱库存」勾选框 —— 不勾就只记「做过」、不动库存

**顺手把原来的「做过」按钮并进了这个流程**：两个按钮都表示「我做了这道菜」，
会让人不知道点哪个；而勾选框正好覆盖了「只记录、不动库存」的旧用法。

做菜会记一笔 `MealHistory(action="cook")`，喂给口味画像（策划书第七节）。

## 测试

| | 数量 | 说明 |
|---|---|---|
| 后端端到端 | **251 项** | 从 196 扩到 251 |
| HTTP 冒烟 | **62 项** | 打真实服务，验序列化契约 |
| 客户端单元测试 | **13 项** | 原有 8 项 + 新增 5 项 `FamilyContractTest` |

新增覆盖：做菜扣库存 20 项、家庭组 35 项（含跨账号共享、只读权限、解散）。

### 客户端契约测试抓出的一个真 bug（值得单独讲）

「我有没有加入家庭」这个状态，最初的设计是**没加入时返回裸 `null`**，
客户端接口签名写 `suspend fun getFamily(): FamilyOut?`。看着很干净。

**但它根本跑不通。**

Retrofit 从返回类型推序列化器时，**Kotlin 的可空标记在 Java 的 `Type` 里丢掉了**，
拿到的是非空的 `FamilyOut.serializer()`。给它喂一个 JSON 字面量 `null`，
kotlinx-serialization 直接抛 `JsonDecodingException`。

后果：**没加入家庭的用户打开家庭页，看到的是「出错了」，
而不是本该显示的创建/加入入口** —— 新用户第一次点进来就是这个样子。

这个 bug 只在真机上才暴露，而当时手机连不上。是靠
`FamilyContractTest`（用 MockWebServer 跑真实 HTTP 栈）才抓出来的。

**修法**：后端不再返回裸 `null`，改成永远返回对象、用 `joined` 字段当开关。
「有没有家庭」是一个**字段**，不是一个可能不存在的响应体。

`FamilyContractTest` 里还留了一个**反例测试**
（`control_bareNullBodyBreaksNullableReturnType`），把「裸 null 不行」
固定下来 —— 免得下一个人又觉得「返回 null 更干净」而改回去。
反例的价值在于证明那些正面测试**真的有验证能力**：哪天 Retrofit 改了行为，
反例不再抛异常，就说明这个文件的结论需要重新验证，
而不是默默变成一堆永远为真的空断言。

> 这个项目在「响应体为 null」上已经踩过三次坑了：
> 两次是 204 空响应体（见 `DeleteContractTest`），
> 这次是 200 + 字面量 null。**结论：客户端不要指望接住 null 响应体。**

## 正式包的签名验证

生成 `release.jks` 之后，一直没人验证过它能不能真的签出正式包 ——
CI 上因为没配 Secrets，一直用的是 debug 签名。

这次在本地跑了一遍 `assembleRelease`，然后用 `apksigner` 查证书：

| | 证书 DN |
|---|---|
| debug 包 | `C=US, O=Android, CN=Android Debug` |
| release 包 | `CN=FridgeProphet, OU=Mobile, O=FridgeProphet, L=Beijing, ST=Beijing, C=CN` |

release 包用的是自己的密钥，不是 debug 证书 ✓
说明 `keystore.properties` 配置正确、密钥可读、构建脚本正确选中了 release 签名配置。

**这一步必须用 `apksigner verify --print-certs` 查，不能只看「构建成功」。**
因为缺 `keystore.properties` 时 Gradle 会**静默退回 debug 签名**，
构建照样成功、APK 照样能装 —— 只有查证书才能发现。

```bash
cd android
export JAVA_HOME="G:/Android/jdk-17.0.20.1+1"
"G:/Android/Sdk/build-tools/36.0.0/apksigner.bat" verify --print-certs \
  app/build/outputs/apk/release/app-release.apk
```

> 这次验证用的后端地址是局域网 IP（`http://192.168.3.5:8000/`），
> 只是为了验签名。**正式发布前必须换成公网域名重新构建。**

## 还没验证的部分（重要）

**上面 ① ② ③ ⑤ 的界面改动，都还没在真机上跑过。**

原因是 `adb devices` 一直连不上手机。已经验证的是：

- ✅ 后端逻辑（251 项测试）
- ✅ 接口契约（62 项冒烟 + 4 项客户端契约测试）
- ✅ 客户端编译通过
- ✅ APK 打包成功

**没验证的是「在手机上到底长什么样、点起来顺不顺」**，尤其是：

- 配色改动 —— 颜色必须在真机屏幕上看一眼才算数
- 做菜弹窗的输入框和勾选框交互
- 家庭页的创建/加入/成员管理流程
- 折叠箱是否真的不再自动收起

这些等手机连上后补验。
